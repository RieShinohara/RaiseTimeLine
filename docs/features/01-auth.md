# 機能定義書 01：認証（ユーザー登録・ログイン・ログアウト）

> **状態：ドラフト（2026-11-14）。** 「【未決】」は、まだ決まっていない点。「【補足】」は、Claude Code が補った提案（ユーザーの確認待ち）。「【暫定】」は、講義のプロトタイプで見えた内容を、仮に決めた点（講義の実装の回で、違いが分かったら直す）。
> 2026-11-14：講義の認証の実装計画（バックエンド）で、方式と入力の条件が分かった。AUTH-1・AUTH-4 を決定し、登録の項目に**表示名**を加えた。ログインなしの閲覧は、ユーザーが決定した（AUTH-6）。
> 2026-11-15：講義のフロントエンドの実装の動画で、**札が 2 種類（アクセストークン 15 分、リフレッシュトークン 7 日）に変わった**。ユーザーが「講義にそろえる」と決定（AUTH-1 の更新）。画面側の保存場所（AUTH-9）、登録画面の**パスワード確認**も分かった。先生の指示は、前後することがあるので、**最後に動いた実装を基準**にし、食い違いは「暫定」で進める。
> 全体の機能は [機能一覧](../features.md) を参照。

## 1. 概要と目的
- 利用者が、自分のアカウントを作り（登録）、自分として使い始め（ログイン）、使い終える（ログアウト）ための機能
- 「誰が投稿したか」「誰がいいねしたか」「誰が自分の投稿を直せるか」を決める、**すべての機能の土台**
- 登録は、**ログインとは別の画面**で行う（講義の内容）

## 2. 決まっていること
- ユーザー登録とログインは、別の画面
- **登録の入力は、メールアドレス、パスワード、ユーザー名、表示名の 4 つ。画面には、打ち間違いを防ぐ「パスワード確認」の欄も、ある**（画面で 5 欄。パスワード確認は、画面側だけで確かめ、サーバーには送らない）。講義の実装の画面で確認（2026-11-15）。プロトタイプでは、メール・パスワード・パスワード確認・ユーザー名の 4 欄だったが、実装で表示名が加わった（ユーザーが取り入れると決定）
- 【暫定】**ログインは、メールアドレスとパスワード**で行う（AUTH-2。ユーザー名では、ログインしない）。実装計画の API も、メールアドレスとパスワード
- **登録が済んだら、「登録が完了しました。ログインしてください。」と表示して、ログインの画面へ進み、もう一度、メールアドレスとパスワードを入力してログインする**（自動ログインはしない）（AUTH-3。講義のプロトタイプで確認。2026-11-15 に、再確認）
- メールアドレスは、重複できない。大文字小文字は区別しない（【補足】同じアドレスを、2 つのアカウントに使えない）
- **ユーザー名**（`testuser` のような ID。X の「@ID」にあたる）：重複できない。登録後は変えられない（PF-1）。ユーザー検索・プロフィールへの移動に使う
- **表示名**（`テスト` のような、画面に出す名前）：日本語も使える。**重複してよい**（【補足】）。**プロフィールの編集で変えられる**（2026-11-14 決定）
- 人の表示は、「表示名」と「@ユーザー名」を並べる（講義の実装の画面で確認。ログイン後に、「ようこそ、○○さん」と、「@ユーザー名」が出る。2026-11-15）。細かい見せ方は、画面設計で決める
- **認証の方式は、JWT（トークン方式）＋ Spring Security。札は 2 種類**：アクセストークン（15 分）と、リフレッシュトークン（7 日）（AUTH-1。2026-11-14 決定、2026-11-15 に更新。下の「3.5」）
- メールアドレスは、**他の人には見せない**（プロフィール・投稿・検索には、出さない。本人の確認用だけ。【補足】）
- 【補足】確認メールの送信（メールアドレスが本物かの確認）は、作らない（学習の範囲を超えるため。将来の候補）
- パスワードは、そのままの形では保存しない（ハッシュ化。**BCrypt**。[非機能要件](../non-functional-requirements.md) 4）
- 認証が必要な操作（投稿・コメント・いいね・フォロー・編集・削除）は、ログインしていないと、できない（サーバー側で拒否する）
- **ログインしていなくても、見るだけはできる**（AUTH-6。2026-11-14 ユーザー決定。どんなサービスか、使う前に見られるように）。
  - 見られる：「全体」のタイムライン、投稿の詳細（コメントつき）、プロフィール、フォロー中・フォロワーの一覧、いいねした人の一覧、ユーザー検索
  - 見られない：「フォロー中」のタイムライン（「誰が自分か」が必要なため）
  - ログインしていない人が、いいね・コメント・フォローなどを押したときは、ログインの画面へ案内する
  - 講義の実装計画の最初の設定は「登録・ログイン以外は、すべて認証必須」だった。**これは、認証だけを作る段階の設定で、ユーザーの方針とは違う。** 実装のとき、見るだけの API を、ログイン不要にする（問題が出たら、メンターに相談する）
- ログインの失敗の文言は、「メールアドレスかパスワードが違います」とし、どちらが違うかは教えない（【補足】）

## 3. 操作の流れ（ユースケース）

### UC-1: ユーザー登録する
- 利用者：新しい利用者
- 目的：アカウントを作る
- 事前条件：ログインしていない
- 基本の流れ：
  1. 「ユーザー登録」の画面を開く
  2. メールアドレス、パスワード、パスワード確認、ユーザー名、表示名を入力する
  3. 「登録」を押す
  4. アカウントが作られ、「登録が完了しました。ログインしてください。」と表示されて、ログインの画面へ進む（ログインした状態にはならない。ログインの画面で、もう一度入力する）
- 例外の流れ：
  - パスワードと、パスワード確認が、違うときは、登録できず、理由を表示する（画面側で確かめる）
  - メールアドレス、またはユーザー名が、すでに使われているときは、登録できず、理由を表示する（API は 409）
  - メールアドレスの形が正しくないときは、登録できず、理由を表示する
  - 入力が、3.5 の条件を満たさないとき（空、文字数、使える文字、パスワードの条件）は、登録できず、理由を表示する（API は 400）

### UC-2: ログイン・ログアウトする
- 目的：自分のアカウントで使い始める／終える
- 基本の流れ：
  1. 「ログイン」の画面で、メールアドレスとパスワードを入力して、「ログイン」を押す
  2. 成功したら、タイムラインの画面へ進む
  3. 使い終わったら、「ログアウト」を押す。ログインの画面へ戻る（画面側が、持っている 2 つの札を捨て、**サーバー側でも、リフレッシュトークンを無効にする**。3.5）
- 例外の流れ：
  - メールアドレスかパスワードが違うときは、ログインできず、「メールアドレスかパスワードが違います」と表示する
  - ログインしていない状態で、ログインが必要な画面（「フォロー中」など）や操作（投稿・いいねなど）を開いたときは、ログインの画面へ案内する（【補足】）
  - アクセストークン（15 分）が切れたときは、**自動で、新しい札に交換する**（利用者は気づかない。3.5）。リフレッシュトークン（7 日）も切れたときは、ログインの画面へ案内する（【補足】）

### 3.5 認証の仕組み（講義の実装計画。2026-11-14 決定、2026-11-15 に更新。AUTH-1）
- **JWT**（署名つきの札）を使うトークン方式。**Spring Security** で実装する。普段の通信では、サーバーは、ログインの状態を持たない（STATELESS）
- **札は 2 種類**（2026-11-15。ユーザーが「講義にそろえる」と決定。最初の計画は、24 時間の JWT 1 つだった）：
  | 札 | 有効期限 | 中身・保存 | 役割 |
  |---|---|---|---|
  | **アクセストークン** | **15 分** | JWT。中身は、持ち主の ID と、メールアドレス。署名は HMAC-SHA256。サーバーは、保存しない | 普段の通信で見せる。短命なので、盗まれても被害が短い |
  | **リフレッシュトークン** | **7 日** | **JWT ではなく、UUID（ランダムな文字列）**。**サーバーの DB に保存**する（[データ設計](../database-design.md) の REFRESH_TOKEN） | 期限切れのアクセストークンを、新しい札に**交換するためだけ**に使う |
- ログインに成功すると、サーバーが、**2 つの札**を返す。画面側は、アクセストークンを、**Authorization ヘッダー（Bearer）** に付けて送る。サーバーが、署名と期限を確かめる
- **アクセストークンが切れたら**、画面側が、リフレッシュトークンを送って、新しいアクセストークンをもらう。7 日たって、リフレッシュトークンも切れたら、もう一度ログインする
- **ログアウト・取り消し**：サーバーが、DB のリフレッシュトークンを「無効（revoked）」にする。無効になったものは、もう使えない。「その人の分を、全部無効にする」部品（`revokeAllByUserId`）は、**書いてあるが、使う API は、まだない**（パスワード変更・退会を作るときに使う。品質チェック B2）。アクセストークンは、15 分で切れるので、取り消さなくても、短い間の心配で済む
- 画面側は、**localStorage** に、2 つの札と、ユーザー情報（表示名など）を保存する（AUTH-9）。ユーザー情報に、**パスワード（ハッシュを含む）は、入れない**（【補足】）
- **CSRF 対策は無効**（Cookie を使わず、ヘッダーで送る方式のため）。**CORS** は、画面の URL（開発では `http://localhost:5173`）だけを許可する
- **署名の鍵（secret）は、リポジトリに入れない**（`.env` などに置く。CLAUDE.md の 4）
- 札の中身は、読めてしまうので、秘密（パスワードなど）は入れない
- API の形（講義の例）：登録 `POST /api/auth/register`（成功 201、重複 409、入力の条件違反 400）、ログイン `POST /api/auth/login`（成功 200 ＋ JWT）
- 札の保存場所（画面側）：localStorage（AUTH-9。2026-11-15 決定）。**弱点**：悪いスクリプトを埋め込まれる攻撃（XSS）で、札を読まれる。リフレッシュトークン（7 日）も同じ所にあるが、サーバー側で無効にできる。**守りの土台は、React の標準の書き方を守り、XSS を起こさないこと**（[非機能要件](../non-functional-requirements.md) 4、[学習ノート](../../notes/01-auth-basics.md)）

### 3.6 入力の条件（AUTH-4。2026-11-14 決定。講義の実装計画のとおり）
| 項目 | 条件 |
|---|---|
| メールアドレス | 空は不可。メールの形。255 文字まで |
| パスワード | 空は不可。8 文字以上。**英字と数字を、それぞれ 1 文字以上含む** |
| ユーザー名 | 空は不可。2〜30 文字。**英数字とアンダースコア（_）だけ** |
| 表示名 | 空は不可。50 文字まで |
- 確認は、サーバー側（Spring の validation）で必ず行い、画面側でも行う
- パスワードの長さの上限は、**72 文字**（BCrypt が扱えるのは 72 バイトまでのため）。**使える文字は、半角の英数字と記号（ASCII の `!`〜`~`。スペース、日本語、全角は不可）だけ**（2026-11-16 ユーザーが決定。品質チェック B1。日本語を含むと、72 文字以内でも 72 バイトを超えて、500 エラーになっていた。半角だけなら、72 文字＝72 バイトで収まる）。サーバー・画面とも同じ検査。ログインで、72 バイトを超える入力が来たときは、照合せずに、401 にする

## 4. 画面に出るもの
- ユーザー登録の画面：メールアドレス、パスワード、パスワード確認、ユーザー名、表示名の入力欄、「登録する」ボタン、ログイン画面へのリンク（「アカウントをお持ちの方は ログイン」）
- ログインの画面：メールアドレス、パスワードの入力欄、「ログイン」ボタン、登録画面へのリンク
- ログイン後の画面の見出し：「ログアウト」ボタン、自分のプロフィールへの入口
- ログインしていないときの見出し：「ログイン」「ユーザー登録」のボタン
- 詳細は、実装した画面（[学習ノート 03](../../notes/03-auth-implementation.md)）と、上の記述が正（画面は、実装済み。プロフィールへの入口は、プロフィールの機能のときに足す）

## 5. 使うデータ
- USER（メールアドレス、ユーザー名、表示名、パスワードのハッシュ）。[データ設計](../database-design.md) 2.1
