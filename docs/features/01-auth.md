# 機能定義書 01：認証（ユーザー登録・ログイン・ログアウト）

> **状態：ドラフト（2026-11-14）。** 「【未決】」は、まだ決まっていない点。「【補足】」は、Claude Code が補った提案（ユーザーの確認待ち）。「【暫定】」は、講義のプロトタイプで見えた内容を、仮に決めた点（講義の実装の回で、違いが分かったら直す）。
> 2026-11-14：講義の認証の実装計画（バックエンド）で、方式と入力の条件が分かった。AUTH-1・AUTH-4 を決定し、登録の項目に**表示名**を加えた。ログインなしの閲覧は、ユーザーが決定した（AUTH-6）。
> 全体の機能は [機能一覧](../features.md) を参照。

## 1. 概要と目的
- 利用者が、自分のアカウントを作り（登録）、自分として使い始め（ログイン）、使い終える（ログアウト）ための機能
- 「誰が投稿したか」「誰がいいねしたか」「誰が自分の投稿を直せるか」を決める、**すべての機能の土台**
- 登録は、**ログインとは別の画面**で行う（講義の内容）

## 2. 決まっていること
- ユーザー登録とログインは、別の画面
- **登録の入力は、メールアドレス、パスワード、ユーザー名、表示名の 4 つ**（講義の実装計画で確認。2026-11-14。プロトタイプでは 3 つに見えたが、実装で表示名が加わっていた。ユーザーが取り入れると決定）
- 【暫定】**ログインは、メールアドレスとパスワード**で行う（AUTH-2。ユーザー名では、ログインしない）。実装計画の API も、メールアドレスとパスワード
- 【暫定】**登録が済んだら、ログインの画面へ進み、もう一度、メールアドレスとパスワードを入力してログインする**（自動ログインはしない）（AUTH-3）
- メールアドレスは、重複できない。大文字小文字は区別しない（【補足】同じアドレスを、2 つのアカウントに使えない）
- **ユーザー名**（`testuser` のような ID。X の「@ID」にあたる）：重複できない。登録後は変えられない（PF-1）。ユーザー検索・プロフィールへの移動に使う
- **表示名**（`テスト` のような、画面に出す名前）：日本語も使える。**重複してよい**（【補足】）。**プロフィールの編集で変えられる**（2026-11-14 決定）
- 【補足】投稿・コメントなどの人の表示は、「表示名」と「@ユーザー名」を並べる。細かい見せ方は、画面設計で決める
- **認証の方式は、JWT（トークン方式）＋ Spring Security**（AUTH-1。2026-11-14 決定。下の「3.5」）
- メールアドレスは、**他の人には見せない**（プロフィール・投稿・検索には、出さない。本人の確認用だけ。【補足】）
- 【補足】確認メールの送信（メールアドレスが本物かの確認）は、作らない（学習の範囲を超えるため。将来の候補）
- パスワードは、そのままの形では保存しない（ハッシュ化。**BCrypt**。[非機能要件](../non-functional-requirements.md) 4）
- 認証が必要な操作（投稿・コメント・いいね・フォロー・編集・削除）は、ログインしていないと、できない（サーバー側で拒否する）
- **ログインしていなくても、見るだけはできる**（AUTH-6。2026-11-14 ユーザー決定。どんなサービスか、使う前に見られるように）。
  - 見られる：「全体」のタイムライン、投稿の詳細（コメントつき）、プロフィール、フォロー中・フォロワーの一覧、いいねした人の一覧、ユーザー検索
  - 見られない：「フォロー中」のタイムライン（「誰が自分か」が必要なため）
  - ログインしていない人が、いいね・コメント・フォローなどを押したときは、ログインの画面へ案内する
  - 講義の実装計画の最初の設定は「登録・ログイン以外は、すべて認証必須」だった。**これは、認証だけを作る段階の設定で、ユーザーの方針とは違う。** 実装のとき、見るだけの API を、ログイン不要にする（問題が出たら、メンターに相談する）
- ログインの失敗の文言は、「メールアドレスかパスワードが違います」とし、どちらが違うかは教えない（【補足】）

## 3. 操作の流れ（ユースケース）

### UC-1: ユーザー登録する
- 利用者：新しい利用者
- 目的：アカウントを作る
- 事前条件：ログインしていない
- 基本の流れ：
  1. 「ユーザー登録」の画面を開く
  2. メールアドレス、パスワード、ユーザー名、表示名を入力する
  3. 「登録」を押す
  4. アカウントが作られ、ログインの画面へ進む（【暫定】ログインした状態にはならない。ログインの画面で、もう一度入力する）
- 例外の流れ：
  - メールアドレス、またはユーザー名が、すでに使われているときは、登録できず、理由を表示する（API は 409）
  - メールアドレスの形が正しくないときは、登録できず、理由を表示する
  - 入力が、3.5 の条件を満たさないとき（空、文字数、使える文字、パスワードの条件）は、登録できず、理由を表示する（API は 400）

### UC-2: ログイン・ログアウトする
- 目的：自分のアカウントで使い始める／終える
- 基本の流れ：
  1. 「ログイン」の画面で、メールアドレスとパスワードを入力して、「ログイン」を押す
  2. 成功したら、タイムラインの画面へ進む
  3. 使い終わったら、「ログアウト」を押す。ログインの画面へ戻る（JWT は、サーバーが状態を持たないので、ログアウトは、画面側が、持っている JWT を捨てること）
- 例外の流れ：
  - メールアドレスかパスワードが違うときは、ログインできず、「メールアドレスかパスワードが違います」と表示する
  - ログインしていない状態で、ログインが必要な画面（「フォロー中」など）や操作（投稿・いいねなど）を開いたときは、ログインの画面へ案内する（【補足】）
  - 有効期限（24 時間）が切れたときは、ログインの画面へ案内する（【補足】）

### 3.5 認証の仕組み（講義の実装計画。2026-11-14 決定。AUTH-1）
- **JWT**（署名つきの札）を使うトークン方式。**Spring Security** で実装する。サーバーは、ログインの状態を持たない（STATELESS）
- ログインに成功すると、サーバーが JWT を返す。**有効期限は 24 時間**。中身は、持ち主の ID と、メールアドレス。署名は HMAC-SHA256
- 画面側は、以後の通信で、JWT を **Authorization ヘッダー（Bearer）** に付けて送る。サーバーが、署名と期限を確かめる
- **CSRF 対策は無効**（Cookie を使わず、ヘッダーで送る方式のため）。**CORS** は、画面の URL（開発では `http://localhost:5173`）だけを許可する
- **署名の鍵（secret）は、リポジトリに入れない**（`.env` などに置く。CLAUDE.md の 4）
- 札の中身は、読めてしまうので、秘密（パスワードなど）は入れない
- API の形（講義の例）：登録 `POST /api/auth/register`（成功 201、重複 409、入力の条件違反 400）、ログイン `POST /api/auth/login`（成功 200 ＋ JWT）
- 札の保存場所（画面側）は、画面の実装の回で決める（【未決】。AUTH-9）

### 3.6 入力の条件（AUTH-4。2026-11-14 決定。講義の実装計画のとおり）
| 項目 | 条件 |
|---|---|
| メールアドレス | 空は不可。メールの形。255 文字まで |
| パスワード | 空は不可。8 文字以上。**英字と数字を、それぞれ 1 文字以上含む** |
| ユーザー名 | 空は不可。2〜30 文字。**英数字とアンダースコア（_）だけ** |
| 表示名 | 空は不可。50 文字まで |
- 確認は、サーバー側（Spring の validation）で必ず行い、画面側でも行う
- パスワードの長さの上限は、決まっていない（【補足】実装のとき、BCrypt の制限に合わせて決める）

## 4. 画面に出るもの
- ユーザー登録の画面：メールアドレス、パスワード、ユーザー名、表示名の入力欄、「登録」ボタン、ログイン画面へのリンク
- ログインの画面：メールアドレス、パスワードの入力欄、「ログイン」ボタン、登録画面へのリンク
- ログイン後の画面の見出し：「ログアウト」ボタン、自分のプロフィールへの入口
- ログインしていないときの見出し：「ログイン」「ユーザー登録」のボタン
- 詳細は、画面設計（これから）で定める

## 5. 使うデータ
- USER（メールアドレス、ユーザー名、表示名、パスワードのハッシュ）。[データ設計](../database-design.md) 2.1
