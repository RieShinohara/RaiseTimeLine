# 復習 B：パスワード・ハッシュ・CORS・CSRF

2026-11-18。復習 A（[ノート 08](08-review-a.md)）で、JWT と 2 種類の札は扱った。B は、**認証の残り**（パスワードの扱い、ログイン失敗の文言、CORS と CSRF）。番号は B だが、A・C・D のあとに足した。

## 前提：パスワードの流れ
```
登録： パスワード「password1」 → 変換（BCrypt）→ DB には「$2a$10$…（長い文字列）」だけを保存
ログイン： 入力 → 同じ変換をして → DB の文字列と照らす（一致すれば OK）
```
```java
user.setPasswordHash(passwordEncoder.encode(request.password()));    // 登録のとき
passwordEncoder.matches(request.password(), user.getPasswordHash())  // ログインのとき
```

## 問題と答え

**B-1. DB に、パスワードそのものではなく、ハッシュを保存するのは、なぜ？**
- 自分の答え：そのまま保存すると、DB に侵入されたとき、情報を抜き出される。ハッシュ化なら、すぐには解読されない
- 補足：
  - ハッシュは、**元に戻せない変換**（一方向）。攻撃者にできるのは、いろいろなパスワードを試して、同じハッシュになるかを探す**総当たり**だけ
  - **BCrypt は、わざと遅い**。さらに、**毎回違う「塩」を混ぜる**ので、同じパスワードでも、毎回違うハッシュになる。「よくあるパスワードのハッシュの一覧表」が、使い回せない
  - 人は、別のサービスでも、**同じパスワードを使い回す**。平文が漏れると、被害が、他のサービスに広がる

**B-2. ログインで、メールアドレスが違うときも、パスワードが違うときも、同じ文言を返すのは、なぜ？**
- 自分の答え：どちらが合っているかを、悪意のある相手に、教えないため
- 補足：「このメールアドレスは、登録されている」と分かるだけで、その人に絞った攻撃（パスワードの総当たり、フィッシングメール）ができる。これを**ユーザー列挙の防止**という（[ノート 03](03-auth-implementation.md) の Q1）

**B-3. CORS は、「悪い人が、curl で、直接 API を叩く」ことを、防げる？**
- 自分の答え：分からない
- 答え：**防げない**。**CORS は、サーバーを守る仕組みではなく、ブラウザの決まりごと**
  - 決まり：別のサイト（オリジン）で動くプログラムには、サーバーが「この住所の人には、渡してよい」と言うまで、**ブラウザは、返事を渡さない**
  - 守られているのは**利用者**。悪いサイトのプログラムが、あなたのブラウザを使って、別のサイトの返事を、勝手に読むのを防ぐ
  - **curl は、ブラウザではない**。CORS の決まりは、関係ない。サーバーは、普通に返事をする
  - **本当の守りは、認証（札）**

| 仕組み | 守る相手 | どこで働く |
|---|---|---|
| CORS | 利用者（悪いサイトから） | ブラウザ |
| 認証（札）・本人確認 | サーバーのデータ | サーバー |

**B-4. 札を Cookie に入れると、CSRF の心配が戻るのは、なぜ？**
- 自分の答え：Cookie は、認証を通ったときに付けられるので、悪意のあるアクセスでも、認証を通ったとみなされる
- 補足（決め手）：**Cookie は、ブラウザが、自動で付ける。悪いサイトの画面から送られた通信にも、付けてしまう**

```
① あなたが、このアプリにログイン（Cookie に札が入る）
② 別の、悪いサイトを開く
③ 悪いサイトの画面が、「この SNS に、投稿を削除」という通信を、あなたのブラウザから送らせる
④ ブラウザは、「この SNS 宛てだから」と、Cookie を、自動で付けて送る
⑤ サーバーは、本物のログイン済みの人だと思って、実行してしまう
```
- **ヘッダーの札**は、画面のプログラムが、**自分で付ける**。悪いサイトのプログラムは、このアプリの保存場所（localStorage）を読めないので、付けられない → CSRF が成り立たない
- **どちらも完璧ではない。** ヘッダー方式は、**XSS**（正規のサイトの中に、悪いプログラムを入れられる攻撃）に弱い。本番では、Cookie の中でも、**HttpOnly**（プログラムから読めない）の検討が要る（[ノート 01](01-auth-basics.md)）

## 質問と整理：CORS があるのに curl が使えるのは？ XSS は curl の攻撃？
復習のあとに、ユーザーから出た疑問（「CORS は、指定のオリジンだけを許可する。でも curl は使える。他の仕組みがあるのか。curl は、バックエンドで動く品質チェックのツールか。curl を使った攻撃が XSS か。React の標準の書き方を守る、とは、そのこと？」）。**混ざっていた所が 3 つ**あった。

### ① CORS：理解は合っている
- 許可するのは、**オリジン**（「http か https」＋「ドメイン」＋「ポート番号」の 3 つの組）。ポート番号だけではない

### ② curl は、バックエンドの一部でも、品質チェックの道具でもない
- curl は、**世界中で使われている、ごく普通のコマンド**（Windows・Mac・Linux に最初から入っている）。「この URL に、通信を送る」だけの道具
- 私たちは、**自分のアプリの動きを確かめるために、使っただけ**。悪い人も、同じ道具を使える。curl でなくても、Python、Postman、自作のプログラムなど、**HTTP の通信を送れる物なら、何でも**使える
- つまり、「バックエンドが、curl を許す仕組みがある」のではなく、**「公開された API は、誰からの通信にも、そもそも答える」**
- **「他に仕組みがあるのか」の答えは、「はい。認証と、サーバー側のチェック」**。curl でもブラウザでも関係なく、全部の通信に働く

| 守る仕組み | どんな通信から守る |
|---|---|
| 認証（札） | 札がない・偽物 → 401 |
| 権限のチェック | 札は本物でも、他人の物 → 403 |
| 入力のチェック | 280 文字超、空の本文 → 400 |
| `#{}`（SQL） | 悪い文字列を、命令に化けさせない |

CORS は、この中で、**ブラウザ経由の、特別な場面**だけの決まりごと。

### ③ XSS は、curl を使った攻撃ではない
| | 何をする | どこから |
|---|---|---|
| curl などで、直接 API を叩く | サーバーに、直接、変な通信を送る | 悪い人の、自分の PC から |
| **XSS** | **こちらの画面の中で、悪いプログラムが、動いてしまう** | **正規の画面の中**（利用者のブラウザの中） |

```
① 悪い人が、投稿の本文に、悪いプログラム（<script>…</script>）を書いて投稿する
② もし、画面が、本文を「HTML」として、そのまま表示してしまうと…
③ 他の人が、その投稿を見たとき、悪いプログラムが、その人のブラウザの中で動く
④ そのプログラムは、その人の札（localStorage）を読み取って、悪い人に送れてしまう
```
- 悪いプログラムは、**正規の画面の中で、利用者本人として**動く。サーバーには、本物の利用者の通信に見えるので、**認証（札）では防げない**

### ④ 「React の標準の書き方を守る」は、XSS の対策
```tsx
<Typography>{post.body}</Typography>   // 標準の書き方。本文は「ただの文字」として表示される
```
- React は、`{post.body}` を HTML として解釈しない。`<script>` と書かれても、文字として表示される
- **やってはいけない**のは、`dangerouslySetInnerHTML`（名前に「危険」と書いてある、特別な書き方）。本文が HTML として解釈されてしまう
- `PostCard.tsx` は標準の書き方。**テストもある**（[ノート 06](06-timeline-frontend.md)）。品質チェックで、`dangerouslySetInnerHTML` を使っていないかを調べたのも、この理由

### まとめ：攻撃の種類と、守る場所
| 攻撃 | 何を守る | 守りの場所 |
|---|---|---|
| curl などで、直接 API を叩く | サーバーのデータ | **サーバー**（認証・権限・入力チェック） |
| CSRF（別のサイトが、ブラウザをだます） | 利用者 | **札を、ヘッダーで送る**ことで、成り立たなくする |
| XSS（正規の画面の中で、悪いプログラムが動く） | 利用者の札 | **React の標準の書き方**（本文を、文字として表示） |

守る場所が、**3 か所に分かれている**。1 つだけでは、足りない（品質チェックの「3 枚の網」と、同じ考え方）。

### 次回の復習の問題
> 「悪い人が、curl で、他人の投稿を削除しようとした」ときと、「悪い人が、投稿に、悪いプログラムを書いた」とき。**それぞれ、どこで、止まりますか？**
>
> （答えの方向：前者は、**サーバー**（札がなければ 401、他人の投稿なら 403）。後者は、**画面**（React が、文字として表示するので、動かない）。）

## 学んだこと
- **「利用者を守る仕組み」と「サーバーを守る仕組み」は、別物。** CORS は前者、認証は後者。**画面のチェックは親切、サーバーのチェックは守り**（復習 A の A-3）と、同じ形の話
- 同じ文言にする、ハッシュにする、は、**「悪い人に、ヒントを与えない」「漏れても、被害を小さくする」**という、同じ考え方
- 難しい問題（B-3、B-4）は、「分からない」で、よい。どこから分からないかが、分かる
