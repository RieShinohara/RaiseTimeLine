# 復習 F：Controller・Service・Mapper、401 と 403、主キー・外部キー・CHECK

2026-11-22。復習 E（[ノート 22](22-review-e.md)）の続き。重点は「Function（裏側の見えない仕組み）」。「単語の意味 → 仕組み → 形式」の順で、問題と自分の答えの形で確かめた。実物は、[V5](../backend/src/main/resources/db/migration/V5__create_comments.sql)（外部キー）と [V6](../backend/src/main/resources/db/migration/V6__create_follows.sql)（主キーの組み合わせ・CHECK）。

## 復習 1：Controller・Service・Mapper

### 問題と自分の答え
「それぞれ、何をする係か」→
- Controller：「画面の API リクエストを受け取り、条件に合うかを確認する。OK なら Service に送り、Service からレスポンスを受け取る」
- Service：「API リクエストを確認して実行する所。Mapper に送り、Mapper から DB の必要なデータを受け取る」
- Mapper：「Service から送られたリクエストを、DB に渡すために SQL に値を入れて DB の処理をし、必要なデータを Service に返す」

### 補足
- 流れ（Controller → Service → Mapper → DB、そして返る）は正解。
- **2 つの「確認」は、見るものが違う。** これが、課題の Q9「責務の境界」の答えの材料になる。

| | Controller の確認 | Service の確認 |
|---|---|---|
| 見るもの | 形（空？ 長すぎ？） | 中身の決まり（存在する？ 本人？） |
| たとえ | 受付で「用紙に書き漏れがないか」 | 担当者が「この人に、その手続きの権限があるか」 |

- **Repository ＝ Mapper。** 一般的な設計の言葉では「Repository」。MyBatis では「Mapper」と呼ぶ。役割は同じ（SQL を DB に運ぶ係）。
- **宅配便のたとえ**（ユーザーが思いついた「Mapper は運送担当」）：

| 宅配便 | アプリ | 役割 |
|---|---|---|
| 受付の窓口 | Controller | 伝票の書き漏れを見る |
| 荷物の担当者 | Service | 「送ってよい荷物か」を判断する |
| 運送担当 | Mapper | 中身は見ない。依頼どおり運ぶだけ |
| 届け先の倉庫の検品 | DB の外部キー・CHECK | 規則に合わない荷物は、受け取りを断る |

## 復習 2：401 と 403

### 問題と自分の答え
「401 と 403 の違い」→「401 は、認証がないか、有効期限が切れている。403 は、権限がないリクエスト」

### 補足
- 正解。言い換えると、**401 ＝誰か分からない**（札がない・期限切れ・壊れている）、**403 ＝誰かは分かったが、その操作は許されていない**（例：他人の投稿を消そうとした）。
- たとえ：401 は「入館証を持っていない」、403 は「入館証はあるが、その部屋に入る許可がない」。
- **止まる場所が違う。** 401 は、入口のルール表（Controller の前）で止まる。403 は、Service で止まる（「本人か」を見るのは、中身の決まりだから）。

## 復習 3：主キー・外部キー・CHECK

### 問題と自分の答え
「それぞれ、何を守っているか」→「主キーは、表の中で固有の id になるもの。守る、というのが分からない。外部キーと CHECK も分からない」

### 補足
- **「守る」＝ 間違ったデータが入ろうとしたら、DB が断る**、という意味。

| 言葉 | 一言 | 守ること | 実物 |
|---|---|---|---|
| 主キー | 行を 1 つに決める id | 同じ id の行を 2 つ作らせない。空にさせない（学籍番号のたとえ） | `id BIGSERIAL PRIMARY KEY` |
| 外部キー | 他の表の id を借りる列 | 存在しない相手を指すことを断る | `post_id ... REFERENCES posts (id)`（`REFERENCES`＝参照する） |
| CHECK | 値の条件のルール | 条件に合わない値を断る | `CHECK (follower_id <> followee_id)`（`<>`＝等しくない。自分をフォローできない） |

## 復習 4：フォローの表（follower_id と followee_id）

### 問題と自分の答え
- 主キーが 2 つの列の組み合わせだと、どんな間違いを断るか →「同じ人を 2 回フォローしない、もしくは 2 回フォローされない」（正解）
- 「A さんがフォローしている人」は誰か →「B さん。`follower_id`」（正解。見る列の補足は下）
- 迷った所：「フォロワー数は『私をフォローした人の数』。私を主体にすると、『私は、その数の人からフォローされている』と思ってしまって、ごっちゃになる」

### 補足
- **ごっちゃになる理由を、自分で見つけられた。** 「フォロワー」は、いつも「する人」。私から見て、私に向かってする人が「私のフォロワー」。視点が違うだけで、同じ人を指している。
- **「-er は、する人。-ee は、される人」。** `follower_id` ＝フォローする側、`followee_id` ＝される側。employer（雇う人）と employee（雇われる人）と同じ形。
- 主キーの組み合わせ `(follower_id, followee_id)`：A→B は 1 回だけ。B→A は別の組み合わせなので OK（お互いのフォローはできる）。順番が違えば、別の組み合わせ。
- **探す列と、読む列が入れ替わる。**

| 画面 | 探す列（行を選ぶ） | 読む列（答え） |
|---|---|---|
| 私の**フォロワー**一覧（私をフォローしている人） | `followee_id = 私` | `follower_id` |
| 私の**フォロー中**一覧（私がフォローしている人） | `follower_id = 私` | `followee_id` |

- 前回の訂正とつながる：自分でできるのは、自分を `follower_id` にした行（自分がフォローする）を作る・消すこと。自分を `followee_id` にした行（他の人が、自分をフォローする）は、自分では作れない・消せない。

## 復習 5：DB の守りは、3 枚目の網

### 問題と自分の答え
1. 「存在しない投稿（id = 9999）へのコメントを DB に入れようとすると？」→「Service が 404 を返す？ Mapper は、値が存在しないので、DB に SQL を運ばない？」
2. 「Service で『自分はフォローできない』と確認しているのに、DB にも CHECK を書くのはなぜ？」→「画面を通らない、悪意のあるアクセスが、Service を通らず、直接 DB へ行く可能性を考えて、守っている？」

### 補足と訂正
- 1：Service が 404 を返すのは正解（先に、投稿があるか調べる）。**訂正：Mapper は判断しない。** 存在するかを調べず、SQL をそのまま DB に運ぶ。**断るのは、DB の外部キー。**
- 実際にあった例（[ノート 17](17-backend-qc3-fixes.md) の B11）：いいねを押した人の Service が「投稿はある」と確認した直後に、投稿者が投稿を消すと、確認をすり抜けて SQL が DB に届く。外部キーが断る（その後、404 を返すように直した）。
- 2：正解の 1 つ。守る相手は、悪意だけではない。

| 守る相手 | 例 |
|---|---|
| 悪意のあるアクセス | DB への直接のアクセス（このアプリの DB は、外から入れない設計） |
| 自分たちのバグ | Service の確認に、書き漏れがあった |
| 将来の変更 | 別の API やバッチ処理を足したとき、確認を入れ忘れた |
| 同時アクセス | 2 つの操作が、ほぼ同時に来て、確認の隙間に入った |

- **3 枚の網：**

| 網 | 場所 | 止める物 |
|---|---|---|
| 1 枚目 | Controller | 形の間違い（空・長すぎ） |
| 2 枚目 | Service | 決まりの違反（本人でない・投稿がない） |
| 3 枚目 | DB（主キー・外部キー・CHECK） | 1・2 枚目をすり抜けた物 |
