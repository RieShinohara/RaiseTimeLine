# たまに落ちるテストを、測って直す（F20）

2026-11-22。Issue #161。品質チェックの記録 F20。登録のテストが、テスト全体を並べて動かしたときだけ、5 秒の制限を超えて落ちた。

## 1. 「たまに落ちる」テストは、まず測る
推測で「制限を延ばそう」とする前に、**どこで時間がかかっているか**を測った（`vitest --reporter=verbose` で、テストごとの時間が出る）。

| テスト | 変更前（全体実行） |
|---|---|
| 登録すると、お知らせつきでログイン画面へ進む | **4.4 秒**（制限は 5 秒） |
| パスワード確認が違うとき | 3.4 秒 |
| すでに使われているとき（409） | 3.6 秒 |
| ログインする（比べるため） | 1.4 秒 |

→ 遅いのは、**登録の入力を使う 3 つ**。たまたま、1 つ目が制限の直前で、落ちる日があった。

## 2. 原因：`type` は 1 文字ずつ打つ
`user.type(欄, '文字列')` は、人がキーボードで打つように、**1 文字ずつ**キー入力を送る。登録の画面は 5 欄（合わせて約 50 文字）。1 文字ごとに、キーを押す・離すなどの出来事と、画面の更新が起きる。

テスト全体を並べて動かす（複数のテストファイルを同時に）と、パソコンの頭（CPU）を取り合って、1 つ 1 つが遅くなる。単独で動かすと約 2 秒なのに、全体だと 4 秒台になる理由。

## 3. 直し方：貼り付け（`paste`）
```
await user.click(欄)
await user.paste('文字列')
```
欄を押して、まとめて貼り付ける。**1 欄 1 回**。入る中身は同じ。

| | 変更前 | 変更後 |
|---|---|---|
| 登録のテスト | 4.4 秒 | **2.2〜2.7 秒** |
| パスワード確認が違う | 3.4 秒 | **1.5 秒** |
| 409 | 3.6 秒 | **1.4 秒** |

制限（5 秒）まで、**約 2 倍の余裕**ができた。全体を 3 回動かして、毎回 182 件すべて成功。

## 4. 「制限を延ばす」を選ばなかった理由
`test('…', async () => {…}, 15000)` のように、制限を延ばす方法もある。ただ、これは**遅さを隠すだけ**で、テストは遅いまま。テストが増えるほど、全体が遅くなる。原因（1 文字ずつ打つ）を直せるなら、直すほうがよい。

## 5. わざと壊す確認
貼り付ける値の最初の 1 文字を削ると、登録のテスト（サーバーに送る内容を確かめるもの）が、失敗した。**貼り付けでも、本当に欄に入っている**ことの確認。

## 6. 使い分け
- **`paste`**：入力の「中身」が大事なテスト（登録の内容がサーバーに送られるか）
- **`type`**：1 文字ずつの動きが大事なテスト（文字数の数え方がリアルタイムで変わる、`{Enter}` を押す、など）。検索欄の `Enter` のテストは、`type('山田{Enter}')` のままにしている
