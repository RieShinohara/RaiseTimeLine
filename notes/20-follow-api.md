# フォローの API

2026-11-20。Issue #139。プロフィールとフォロー（機能定義書 07）の、最初の部分。**講義では、プロフィールとフォローの解説はなかった**（講義 30 は「やってみてください」だけ）。だから、いいね（ノート 11）の作りを見本にして、設計は自分たちで決めた。

## 1. 「フォロー」を表で表す

フォローは、「**誰が、誰を**」の組み合わせ。いいね（`post_likes`）が「どの投稿に、どのユーザーが」だったのと、同じ形。

| follower_id | followee_id | 意味 |
|---|---|---|
| 1 | 2 | 1 番の人が、2 番の人をフォローしている |
| 3 | 2 | 3 番の人が、2 番の人をフォローしている |

- **follower**：フォローする側（追いかける人）、**followee**：フォローされる側（追いかけられる人）
- どちらも、**users 表の `id` を借りて書いた列**（ノート 19 の `xxx_id` の読み方）
- 2 番の人の**フォロワー数**（2 番の人を、フォローしている人の数）＝ `followee_id` が 2 の行の数 ＝ 2 人。**数える条件の列は、`followee_id`**
- 1 番の人の**フォロー数**（1 番の人が、フォローしている人の数）＝ `follower_id` が 1 の行の数（これは、プロフィールの API で作る）

## 2. DB の「守り」を 3 重にする

| 守りたいこと | 誰が守るか |
|---|---|
| 同じ組の二重のフォローを作らない | **主キー** `(follower_id, followee_id)`。SQL の `ON CONFLICT DO NOTHING` で、エラーにせず、そのままにする |
| 自分自身をフォローしない | **Service**（400 を返す）と、**DB の `CHECK` 制約**（アプリをすり抜けても、行は作れない） |
| 相手が消えたら、フォローも消える | **外部キーの `ON DELETE CASCADE`** |

「アプリで確かめる」だけでなく、「DB でも止める」と、画面や API を通さない直接の要求や、確認と実行の隙間（ノート 17 の B8・B11）にも強くなる。

## 3. 作ったもの（いいねと、そっくり）

```
PUT/DELETE /api/users/{username}/follow
   FollowController  ← 窓口（ログイン必須）
   FollowService     ← 判断（自分自身か？相手はいるか？）
   FollowMapper(.java + .xml) ← SQL（insert・delete・countFollowers）
   follows 表（Flyway V6）
```

- ユーザー名で相手を探す部品 `UserMapper.findByUsername` を、足した（大文字小文字を区別しない。登録のときの重複の確認と、同じ決まり）
- 返す内容：`followerCount`（相手のフォロワー数）と `following`（いま、フォローしているか）

## 4. テスト（10 件）

- API の通しのテスト 9 件：フォローで数が増える／人数で数える／二重のフォローは 1 回分／フォローしていなくても解除できる／自分自身は 400／**DB の CHECK 制約が自分自身を止める**（Mapper を直接呼ぶ）／ログインなしは 401／存在しないユーザーは 404／大文字小文字を区別しない
- 部品のテスト 1 件：確認と追加の間に、相手が消えた場合（偽物の Mapper で、隙間を作る）→ 404
- **成功を疑う**：わざと、フォロワー数の SQL の条件を `follower_id` に逆にしたら、**3 件が失敗した**。数えるテストが、効いている
- つまずき：壊した XML を戻すため、**先にコピーを取って**から壊した（ノート 19 の教訓）。戻したあと、中身が文字化けしていないことも、確かめた

## 5. 学び方のメモ

- 「自分で、1 つのメソッドを書いてみる」ことを、提案したが、**急ぎすぎて、混乱させた**。コードを書くのは、後でよい（ユーザーの方針）。理解は、**読んで、自分の言葉で答える**形で、進める
