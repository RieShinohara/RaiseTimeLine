# プロフィールの API

2026-11-20。Issue #141。プロフィールとフォロー（機能定義書 07）の 2 つ目。**講義では、解説がなかった**ので、これまでの部品（フォロー・タイムライン）を組み合わせて作った。アイコン画像は、あとに回した。

## 1. 作った API（3 つ）

| メソッド | パス | 誰が使えるか |
|---|---|---|
| GET | `/api/users/{username}` | ログインなしでも OK（プロフィールを見る） |
| PUT | `/api/users/{username}` | **本人だけ**（編集） |
| GET | `/api/users/{username}/posts` | ログインなしでも OK（その人の投稿の一覧） |

- 同じ `/api/users/{username}` でも、**メソッド（GET か PUT か）で、別の API**。GET は「見る」、PUT は「書き換える」
- 見るのは誰でも、書き換えるのは本人だけ。ログインなしで見せるかどうかは、`SecurityConfig` で**道筋ごとに**決める（GET の 2 つだけ許可。PUT は、いままでどおり、ログイン必須）

## 2. 「本人だけ」を、どう守るか

編集の道筋は `/api/users/{username}`（ユーザー名で決まる）。つまり、**誰のプロフィールかは、URL で指定できてしまう**。そこで、サーバーが、次を確かめる。

```
URL のユーザー名 → その人の id を調べる
ログイン中の人の id（札から分かる）と、同じか？
   同じ → 編集してよい
   違う → 403（他の人のプロフィールは、編集できません）
```

- ログインしていなければ、その手前で、401
- **画面で「編集」ボタンを出さなくても、守りにはならない**（ノート 08 の「画面とサーバーの二重チェック」）。curl などで、直接 PUT できてしまうので、**サーバーが断る**

## 3. なぜ `/api/users/me` にしなかったか

`me`（自分）という道筋は、手軽に見える。でも、ユーザー名は **2〜30 文字の英数字**で、`me` も登録できてしまう。すると、「`me` という名前の人のプロフィール」と、「自分のプロフィール」が、ぶつかる。**ぶつかる名前を、道筋に使わない**。

## 4. 既存の部品を使い回す

- **投稿の一覧**：「1 件多く読んで、続きを知る」「いいね数・コメント数・押したかを、まとめて 1 回で数える（N+1 を避ける）」という処理は、`PostService` の中に、すでにあった。それを `toPage` という部品に**取り出して**、タイムラインと、プロフィールの投稿の一覧で、**共有**した（コピーしない）。違いは、SQL の条件（`user_id` で絞る）だけ
- **SQL の共通部分**：`<sql id="postColumns">` を、そのまま `<include>` で使い回せた（ノート 19）
- **フォロー数・フォロワー数**：ノート 20 の `countFollowers` に、`countFollowing`（フォローしている人の数＝`follower_id` で数える）を足した。**どちらの列で数えるか**が、逆にならないよう、テストで、a・b・c の 3 人で確かめた

## 5. 入力の決まりと、その確かめ方

| 項目 | 決まり | テストで確かめたこと |
|---|---|---|
| 表示名 | 必須、前後の空白を取る、50 文字まで | 空白だけ・51 文字は 400、50 文字は OK |
| 自己紹介 | 160 文字まで、空は「未設定」（null） | 161 文字は 400、160 文字は OK、空白だけを保存すると未設定に戻る |
| ユーザー名 | 変えられない | 入力に混ぜても、変わらない |

**境界（ちょうど 50・160 と、その次の 51・161）で確かめる**と、「以下」と「未満」の間違いに気づける。

## 6. 見せてはいけない物

プロフィールの応答に、**メールアドレスとパスワードのハッシュを、入れない**（ログインした本人にだけ必要な情報で、他の人に見せない）。`User` クラスには入っているが、応答用の別の入れ物（`ProfileResponse`）に、**必要な項目だけ**を詰め替える。テストでも、「`email` が、応答に無い」ことを確かめた。

## 7. 確かめたこと

- `gradlew check` 成功。**テストは 93 件**（前回 75 件＋新しい 18 件）、失敗 0、スキップ 0
- **わざと壊した**：投稿の一覧の SQL から、`user_id` の条件を外したら、**3 件が失敗**した（他の人の投稿が混ざる、続きの数が合わない、空のはずが空でない）。コピーを取ってから壊して、戻した
- サーバーを起動して、実際に呼んだ：取得（フォロー数・フォロワー数・`followedByMe`）、本人の編集、他の人の編集（403）、ログインなしの編集（401）、ログインなしの取得、投稿の一覧（`size=1` で、`hasNext` が true）、存在しないユーザー（404）、`size=0`（400）。**編集のあと、投稿の一覧の投稿者の名前（表示名）も、新しい名前になっていた**（投稿に名前を持たせず、毎回 JOIN で読んでいるので、自動で反映される）
- つまずき：テストのメソッド名に、**全角の読点「、」**を入れて、コンパイルが失敗した（Java のメソッド名に使えない）。起動の確認用のスクリプトでは、関数が**バイト列を、1 つずつばらして**返し、本文が壊れて 400 になった（API の不具合ではなく、スクリプトの不具合）。**エラーが出たとき、まず「自分の道具の側」を疑う**
