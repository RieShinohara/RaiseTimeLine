# 認証の実装：ファイルの役割・ログインの流れ・札の自動更新

認証のバックエンド（講義 26。PR #58）と画面（講義 27。PR #62）を作ったときの、**「作ったものが、どう働くか」の理解**のノート（2026-11-15）。
仕組みの理屈（JWT・CSRF など）は [01-auth-basics.md](01-auth-basics.md)、決めたことは [認証の機能定義書](../docs/features/01-auth.md) にある。

## 1. バックエンドのファイルの役割（レストランのたとえ）
`backend/src/main/java/com/example/raisetimeline/auth/` の 12 ファイルは、**お店の仕事の分担**だと考えると分かりやすい。

| お店の役 | ファイル | 役割 |
|---|---|---|
| 入口の警備員 | `SecurityConfig` | 「どの URL は誰でも OK（登録・ログイン）、どれはログイン必須か」の**ルール表**。CSRF は無効、CORS は画面の URL だけ、BCrypt の道具もここで用意 |
| 入口の検問所 | `JwtAuthenticationFilter` | **全リクエストが最初に通る**。`Authorization: Bearer ○○` を見て、本物で期限内なら「この人（ID）としてログイン中」と記録。偽物・期限切れなら何もしない（あとのルール表で 401） |
| ウェイター | `AuthController` | 4 つの窓口（register / login / refresh / logout）。自分では考えず、料理長に渡すだけ |
| 注文票の書式 | `AuthDtos` | 入力と出力の**形**（DTO ＝ データの運び箱）。入力の条件（パスワード 8 文字以上など）もここ。**返す形にパスワードの項目がない**ので、うっかり返す事故が起きない |
| 料理長（頭脳） | `AuthService` | 登録・ログイン・更新・ログアウトの**手順そのもの** |
| 倉庫番 | `UserMapper`、`RefreshTokenMapper` | SQL を書いた係（MyBatis）。値は必ず `#{}` で渡す（`${}` は SQL インジェクションの元） |
| 棚の形 | `User`、`RefreshToken` | DB の 1 行を Java で持つ入れ物（項目と出し入れの口だけ） |
| 会員証の発行係 | `JwtService` | アクセストークン（JWT）の発行と確認だけ。署名の鍵は `.env` の `JWT_SECRET` |
| クレーム係 | `ApiException`、`ApiExceptionHandler` | わざと起こすエラー（409 など）を、`{"message": "..."}` の同じ形で返す |

DB の表は、`src/main/resources/db/migration/V1__...sql`（Flyway）が作る。`users` と `refresh_tokens`。

## 2. ログインを 1 回すると、どう流れるか
1. 画面が `POST /api/auth/login`
2. **検問所**：札はまだないので、素通り
3. **ルール表**：`/api/auth/**` は誰でも OK
4. **ウェイター**（Controller）：入力の条件を確かめる
5. **料理長**（Service）：倉庫番にメールでユーザーを探させ、BCrypt でパスワードを照合
6. **会員証係**（JwtService）が JWT を発行。リフレッシュトークン（UUID）は DB に保存
7. 画面に、2 つの札とユーザー情報を返す

## 3. AuthService の読み方
- **冒頭**：使う道具（倉庫番・BCrypt・JwtService）を、Spring が渡してくれる（**依存性の注入（DI）**）。テストで道具を差し替えやすい。`final` は「受け取ったら入れ替えない」の印
- **`register`**：メールを小文字にそろえる → 重複チェック（409）→ **パスワードをハッシュ化**（`encode`）→ 保存。`DuplicateKeyException` の catch は、「確認から保存までの一瞬に、同時に同じ値で登録された」ときの二重の守り（DB の一意制約が止める）
  - `encode` は、毎回違う「塩」を混ぜるので、同じパスワードでも毎回違うハッシュになる（DB には `$2a$…`）
- **`login`**：`matches` は、入力を同じ方法でハッシュにして、保存済みと照らす。**ハッシュは元に戻せない**ので、照合だけができる
- **`refresh`**：DB に無い（偽物）／`revoked`（ログアウト済み）／期限切れ、のどれかなら 401。大丈夫なら、**アクセストークンだけ**新しく返す
- **`logout`**：削除ではなく、`revoked = true` の印を付ける。存在しない札でもエラーにしない（**何回押しても同じ結果**）
- **`normalizeEmail`**：`trim` と `toLowerCase(Locale.ROOT)`。`Locale.ROOT` は、トルコ語の設定の PC で `I` が変な小文字になる事故を防ぐ決まり文句

## 4. 理解度チェックと答え
**Q1. ログインで、メールが無いときと、パスワードが違うときの文言を同じにするのは、なぜ？**
- どちらが違うかを教えると、悪い人へのヒントになる。「このメールは登録されている」と分かるだけで、次の攻撃（そのアドレスへのパスワード当て、迷惑メール、なりすまし）の足がかりになる。この対策を「ユーザー列挙の防止」という

**Q2. アクセストークンは DB に保存しないのに、リフレッシュトークンは保存するのは、なぜ？**
- 期限の違いだけが理由ではない。決め手は、**自分で自分を証明できるか**

| | アクセストークン（JWT） | リフレッシュトークン（UUID） |
|---|---|---|
| 中身 | ユーザー ID と署名が入っている | ただのランダムな文字列 |
| 本物かの確かめ方 | **署名を計算するだけ**（DB は要らない） | 文字列だけでは分からない。**DB に「発行した」記録が要る** |
| 取り消し | できない（15 分待つ） | **DB の `revoked` を true にすれば、すぐ無効にできる** |

- 覚え方：**計算で確かめられる物は保存しない。確かめられない物は保存する。保存しているから、取り消せる。**
- 短命な JWT は、取り消せなくても被害が短い。長命なリフレッシュトークンは、取り消せるように DB に置く。**役割を分けている**

## 5. 画面の側（講義 27）
`frontend/src/` の構成：

| ファイル | 役割 |
|---|---|
| `api/auth.ts` | 認証 API を呼ぶ関数（札なし）。サーバーの `{"message"}` を取り出す。つながらないときは「サーバーにつながりません」 |
| `api/http.ts` | **ログインが要る API を呼ぶ共通の入口**。札を付ける・401 で自動更新 |
| `auth/tokenStorage.ts` | localStorage の出し入れ。使えなくても落ちない。**読んだユーザー情報は、形（`id` が数、`email`・`username`・`displayName` が文字列）を確かめ、違えばログインしていない状態にする**（品質チェック F2。2026-11-18）。「型を付ける（`as`）」だけでは、実行時には何も確かめない。JSON を読むときは、**中身を、実際に確かめる** |
| `auth/AuthContext.tsx`・`useAuth.ts` | 「今ログイン中の人」を、画面全体で共有する |
| `auth/validators.ts` | 登録の入力チェック（バックエンドと同じ条件。親切のための早めの確認で、本当の確認はサーバー） |
| `pages/`・`components/Header.tsx` | ログイン・登録・トップの画面、ヘッダー |

**札の自動更新**（`http.ts`）：
1. API を呼ぶ → 401（アクセストークンの期限切れ）
2. リフレッシュトークンで `/api/auth/refresh` → 新しいアクセストークン
3. **同じ操作をやり直す**（利用者は気づかない）
- 同時に 401 が何本来ても、更新は **1 回だけ**（同じ札を何度も使わない）
- 更新が 401（無効）なら、札を捨てて、ログアウトの状態にする。**通信が切れただけなら、ログインは切らない**（電波が悪いだけで、ログアウトされたら困る）
- 方式は「401 が来たら更新する」。アクセストークンの期限を、画面側で読まない（簡単で、時計のずれに強い）

## 6. つまずいたこと
| 起きたこと | 原因と対策 |
|---|---|
| 壊れた JSON を送ると、400 ではなく **401** が返った | Spring は、エラーを返すとき、内部で `/error` に転送する。そこが「ログイン必須」だったので、401 に化けた。`/error` を開けて解決。**テストだけでは気づけず、実際に起動して curl で叩いて見つけた** |
| Flyway の移行ファイル（`V1__...sql`）が、コミットされない | `.gitignore` の `*.sql`（DB の書き出しを守るため）が、移行ファイルも無視していた。移行ファイルだけ例外にした |
| JWT の改ざんテストが、一度失敗した | 署名の**末尾に文字を足しても**、符号化の余りで検出されないことがある。署名の**先頭の 1 文字を書き換える**形に直した。**「テストが落ちるか」を確かめられた例** |
| SpotBugs が、`JwtService` のコンストラクターを指摘 | コンストラクターが例外を投げうる（鍵が短いなど）と、「半端な状態のオブジェクト」が残る恐れがある。クラスを `final` にして解決 |
| `.claude/settings.json` に、見覚えのない許可ルールが増えた | 確認の画面で「常に許可」を押すと、自動で書き足される。コミット前に `git diff .claude/settings.json` を見る。確認の画面では「今回だけ許可」を選ぶ |

## 7. 確かめ方（実物で確かめる）
- **curl**：登録 201／重複 409／条件違反 400／ログイン失敗 401（同じ文言）／更新 200／ログアウト 204／ログアウト後の更新 401、を実際に確かめた
- **ブラウザ（DevTools の Network）**：アクセストークンをわざと壊して API を呼ぶと、「401 → refresh 200 → 再送」の 3 行が並ぶ。自動更新が、実物で動いている証拠
- **DB**：`select * from refresh_tokens` で、ログアウト後に `revoked = t` を確かめた。パスワードが `$2a$` で始まるハッシュであることも確かめた（元のパスワードは、どこにも保存されていない）
