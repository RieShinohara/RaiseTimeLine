# いいねの画面：結果を待つ、札を付ける、二重に送らない

2026-11-18。⑥-2（Issue #117）。いいね API（[ノート 11](11-likes-api-n-plus-one.md)）を、画面から使う。

## 2. 気をつけたこと
- **一覧を読むときにも、札が要る。** 以前は、「ログインなしで見られるので、札を付けない」作りだった。ところが、`likedByMe`（自分が押したか）は、**サーバーが、札から「誰か」を知って**返す。札がないと、常に false になる。**期限切れの札も同じ**（サーバーは、401 ではなく「ログインなし」として扱う）ので、読む前に、期限を見て、先に更新する。**新着の件数（ノート 06）で出会った落とし穴と、同じ形**。ログインなしでも使える API でも、「ログイン中の人の分」を返すなら、札が要る
- **結果を待ってから、画面を変える**（LIKE-3）。先に変える方式（楽観的更新）は、体感は速いが、失敗したとき、嘘の数が見える。今は、単純で、数がずれない方を選んだ。サーバーが返した数をそのまま使うので、**他の人がその間に押した分も、正しく反映される**
- **二重に送らない。** 押している間は、その投稿のボタンを押せなくする。さらに、判断には、**`useRef` の「印」**を使う。`useState` だけだと、画面が描き直される前に 2 回目が通ってしまうことがある（印は、すぐ書き換わる）。画面に見せる分（ボタンを押せなくする）は、`useState`
- **押した状態を、色だけで伝えない。** ハートの形（塗りつぶしか、枠だけか）と、`aria-pressed`（押された状態、という印）でも伝える。名前に、投稿者と本文の頭を入れて、読み上げでも、どの投稿のボタンか分かる（品質チェック F7 と同じ考え方）
- **文章の部分（`Typography`）に、`aria-label` を付けない。** 読み上げで、正しく扱われないことがある。数は、ただの文字として出す
- **ログインなしで押されたら、ログインの画面へ。** 画面（PostCard）は、「押された」ことを、呼ぶ側に伝えるだけ。どう案内するかは、呼ぶ側（HomePage）が決める。部品が、ログインの有無を知らなくて済む

## 3. テストで気づいたこと
- **型の検査が、テストの「見本」の足りなさを教えてくれた。** `Post` に項目を足したら、テストの投稿の見本（3 か所）が、型の検査（`tsc`）で、エラーになった。**アプリ本体のコードは、通っていた**。型を付けておくと、「項目を足したときに、直す所」を、機械が教えてくれる
- **私の想定が、ずれていた。** 「ログアウトのボタンを押すと、前の人の押した状態が残る」心配を、テストにしようとした。ところが、ヘッダーのログアウトは、**ログイン画面へ移動する**（トップ画面が消える）ので、その心配は、起きない。**テストが、ファイル全体で動かしたときだけ失敗した**ので、原因を調べて、分かった。**この処理が役に立つのは、トップ画面を開いたまま、ログインが切れたとき**（札の更新も無効）。テストを、その本当の場面に直した
  - 「単独では通るのに、全体では失敗する」は、**タイミングによる揺れ**か、**テストの想定の間違い**のサイン。今回は、後者だった。直したあと、3 回続けて動かして、揺れていないことも確かめた
- **わざと壊して、テストが失敗することを確かめた（3 か所）：** ①一覧を読むときの札付けを外す → 「札を付ける」のテストだけが失敗 ②「ログインなしなら、押した状態を出さない」処理を外す → 「ログインが切れたら消える」のテストだけが失敗 ③「送信中は押せない」を外す → 2 件（カードと画面）が失敗
- **実際のブラウザでも確かめた。** ログインなしの表示、押す（赤いハート・数 1）、読み直しても残る、取り消し（数 0）、ログインなしで押すとログイン画面へ。通信は、`PUT`・`DELETE` が 200。コンソールの警告・エラーなし
