# 認証の基礎：トークン・JWT・CSRF・XSS・CORS

RaiseTimeLine で、初めて出てきた「ログイン（認証）」の仕組みのノート。講義の認証の実装計画（2026-11-14）と、Claude Code との質問・答えで学んだことをまとめた。
決めたことは、[認証の機能定義書](../docs/features/01-auth.md) にある。ここは、**「なぜそうなのか」の理解**を残す場所。

## 1. トークンとは
- **「本物の代わりになる、小さな証拠の札」**。最初に 1 回、本人確認や支払いをして、その証拠として札をもらい、あとは札を見せるだけで済む
- 例：ゲームセンターのメダル、クロークの番号札、遊園地のリストバンド、IC カード
- IT では、**「本人確認が済んだ証拠の札」**（認証トークン）を指すことが多い

**同じ言葉でも、別の意味がある（混ざりやすい）**
| 場面 | 指すもの | 見分けるコツ |
|---|---|---|
| 認証（今回） | ログインした証拠の札（JWT など） | ログイン・API・Authorization・Bearer という言葉が近くにある |
| AI（Claude など） | 文章を区切った、小さな単位 | 料金・上限・文字数・コンテキストという言葉が近くにある |

## 2. なぜ札なのか（パスワードを毎回送らない理由）
- **使いにくさ**：操作のたびに、パスワードを入力することになる
- **安全面**：
  - 送る回数が多いほど、通信の途中で盗み見られる機会が増える
  - パスワードは、長く使う本人の秘密。盗まれると期限なしで悪用され、使い回していれば他のサービスにも被害が広がる
  - サーバーが毎回、重い計算（BCrypt）で確かめることになる
- **札なら**：パスワードを送るのは、ログインの 1 回だけ。札には有効期限がある（私たちは 24 時間）。札にパスワードは入っていない
- **正直な注意**：札も、盗まれたら、その間は悪用される。「完全に安全」ではなく、「パスワードを毎回送るより、被害を小さくできる」

## 3. JWT の構造と、偽造できない理由
**JWT ＝ JSON Web Token**（「JASON」ではない）。ドット（.）で区切られた、左から 3 つの部分でできている。

```
ヘッダー . 本体（ペイロード） . 署名
```

| 部分 | 中身 |
|---|---|
| ヘッダー | どの方式で署名したか（私たちは HMAC-SHA256） |
| 本体 | 持ち主の ID（sub）、メールアドレス（email）、有効期限（exp） |
| 署名 | 「ヘッダー ＋ 本体 ＋ 秘密の鍵」から計算した印 |

- **本体は、隠れていない。** ただの文字の変換（Base64）なので、誰でも読める。だから、**パスワードなどの秘密は、入れない**
- **署名の仕組み**：サーバーだけが持つ「秘密の鍵」で、署名を作る。届いた札は、サーバーが、もう一度署名を計算して、**札の署名と一致するか**を確かめる
- 本体を書き換えると、署名が合わなくなる。署名を作り直すには、秘密の鍵が要る → **偽造できない**（封蝋の印鑑のたとえ）
- サーバーが札を受け入れる条件は、**①署名が合う、かつ ②有効期限が切れていない**
- **秘密の鍵は、最重要。** 公開リポジトリに載ったら、誰でも、他人になりすました札を作れる。`.env` に置き、コミットしない

**札が渡されるのは、ログインのときだけ**
1. メールアドレスとパスワードを送る（`POST /api/auth/login`）
2. サーバーが、パスワードを確かめる（BCrypt）
3. 合っていたときだけ、JWT を返す（200 ＋ JWT）
4. 画面側が、札を保管し、以後の通信で、Authorization ヘッダー（Bearer）に付けて送る
- 登録（`/api/auth/register`）だけでは、札は渡されない（登録後は、ログイン画面へ。AUTH-3）

## 4. セッション方式との違い
**違いは、「ログインしている人の記録を、誰が持つか」。**

| | セッション方式 | トークン方式（JWT。私たちの選択） |
|---|---|---|
| 記録を持つのは | サーバー（名簿） | 利用者の側（札そのものが記録） |
| 渡す物 | ただの番号（セッション ID） | 情報入りの、署名つきの札 |
| 確認のしかた | 名簿で、番号を引く | 署名と期限を計算する |
| ログアウト・無効化 | 得意（名簿から消せば、すぐ無効） | 苦手（札は期限まで有効） |
| サーバーが複数のとき | 名簿の共有が必要 | 得意（札だけで分かる） |

- ホテルのたとえ：セッションは「受付が宿泊者名簿を持ち、客は部屋番号の札だけ持つ」。トークンは「客が、偽造できない宿泊証明書を持ち、受付は名簿を見ずに印を確かめる」
- 「JWT でセッションを管理する」の**セッション**は、「ログイン中の状態」という一般的な意味。方式の名前の「セッション方式」とは別
- **JWT のログアウト**：画面側が、持っている札を捨てるだけ。札そのものは、期限まで有効（学習の範囲では、これで十分という割り切り）
- 私たちは、サーバーが状態を持たない（STATELESS）ので、ロードバランサーの後ろに、サーバーを複数置く構成にも向いている

## 5. CSRF・XSS・CORS の整理
| 略称 | 種類 | 一言で | 私たちの対応 |
|---|---|---|---|
| **CSRF** | 攻撃 | ログイン済みの人のブラウザを、だまして、勝手な操作を送らせる | JWT を、ヘッダーで送るので、成り立たない（CSRF 対策は無効にしてよい） |
| **XSS** | 攻撃 | 正規のサイトの中で、悪いプログラムを動かす | React の標準の書き方を守る。保存場所は、AUTH-9 で決める |
| **CORS** | 守りのルール | 別のオリジンからの通信を、許可するかの設定 | 画面の URL だけを許可。本番では変える |

### CSRF（Cross-Site Request Forgery）
- **ブラウザは、あるサイトに通信するとき、そのサイトが預けた Cookie を、自動で付けて送る。** どのページから通信を始めても同じ
- 攻撃の流れ：ログイン済みのまま、怪しいサイトを開く → 怪しいページが、裏で、RaiseTimeLine への通信を送る → Cookie が自動で付く → サーバーが、本人の操作だと思って実行する
- たとえ：窓口で本人確認が済んでいる人の背後から、送金依頼の紙を、滑り込ませる
- **JWT をヘッダーで送る方式では**、札を付けるのは、RaiseTimeLine の画面のプログラムだけ。悪いサイトは、通信は送れても、札を付けられない（札は、RaiseTimeLine の保管庫にあり、他のサイトからは読めない）→ サーバーが「札がない」と断る（401）
- **ただし、札を Cookie に保存すると、自動で付くので、CSRF の心配が戻る**

### XSS（Cross-Site Scripting）
- 投稿などの本文に、悪いプログラムを紛れ込ませ、**それを見た人のブラウザで、動かす**攻撃。RaiseTimeLine の画面の中で動くので、保管庫（localStorage）の札を読んで、盗める
- SNS は、他の人が書いた文字を、たくさんの人に見せるので、特に狙われやすい（投稿・コメント・表示名・自己紹介が、入口になりうる）
- **守り方**：
  - React は、標準で、文字を「ただの文字」として表示してくれる。これを守る
  - HTML をそのまま出す書き方（`dangerouslySetInnerHTML`）は、使わない
  - サーバー側でも、入力を確かめる
- CSRF との違い：CSRF は、**別の怪しいサイト**から。XSS は、**正規のサイトの中**で

### CORS（Cross-Origin Resource Sharing）
- **オリジン＝プロトコル ＋ ホスト名 ＋ ポート。** 1 つでも違えば、別のオリジン。開発中は、画面（`localhost:5173`）とバックエンド（`localhost:8080`）が、別のオリジン
- ブラウザは、安全のため、別のオリジンの返事を、プログラムに渡さない（同一オリジンポリシー）。そこで、バックエンドが、「このオリジンは許可します」と伝える。これが CORS
- 流れ：ブラウザが、先に確認の問い合わせ（プリフライト）をする → 許可されていれば、本当の通信をする
- 開発中の赤いエラー「CORS policy によりブロックされました」は、許可リストにないオリジンから通信したときに出る
- **勘違いしやすい点**：
  - CORS は、サーバーを守るのではなく、**ブラウザが、利用者を守る**仕組み
  - ブラウザを通さず、直接 API を呼ばれたら、CORS は関係ない。**本当の守りは、認証（札）**
  - 全部を許可（`*`）は、来客リストを無くすのと同じ。避ける
- **本番では、画面の URL に、許可の設定を変える**（開発用のままだと、動かない）

## 6. 札の保存場所（AUTH-9）の比較
画面側が、JWT をどこに保存するか。**未決。画面の実装の回で決める。**

| 保存場所 | CSRF | XSS |
|---|---|---|
| localStorage | 大丈夫（自動で付かない） | 弱い（悪いプログラムが、読める） |
| Cookie（HttpOnly の設定つき） | 対策が必要（自動で付く） | 強い（プログラムから読めない） |

- どちらも、完璧ではない。実際のサービスでも、考え方が分かれる所
- 先生の実装計画（CSRF 無効、Bearer ヘッダー）に合わせると、localStorage が有力。そのかわり、XSS を起こさないことが重要

## 7. パスワードのハッシュ化（BCrypt）
- パスワードは、そのままでは保存せず、**ハッシュ化**（元に戻せない変換）して保存する。方式は **BCrypt**
