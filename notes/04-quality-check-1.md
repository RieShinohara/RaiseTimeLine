# 品質チェック（1回目）で学んだこと

2026-11-16。認証のバックエンドと画面ができた節目で、初めて点検した。結果は [docs/quality-review.md](../docs/quality-review.md)。

## 1. 品質チェックとは
「動く」ことの確認ではなく、「標準的な作りか・安全か・文書と合っているか」を確かめる作業。
- **道具（機械）で確かめる**：テスト、lint（書き方）、Checkstyle・SpotBugs（Java の書き方とバグになりやすい書き方）、JaCoCo（テストが通ったコードの割合）
- **人（と Claude）が読んで確かめる**：道具では見つけられないこと（設計、安全性、文書とのずれ）
- **直すのは、別の PR。** 点検の PR は、見つけたことを記録するだけにする。直す・直さないは、ユーザーが決める

## 2. 今回の結果の読み方
- 道具は、全部成功（テスト 11 件＋画面 27 件、lint 0 件）。それでも、**読んで見つかったことが 13 件**あった。「道具が緑」は、「問題がない」ではない
- **道具の成功を、疑う**：lint がちゃんと働くか、わざと悪いコード（未使用の変数）を書いて、失敗することを確かめた（CLAUDE.md 7）

## 3. 点検で分かった、おもしろい例
- **「部品だけあって、使われていない」コード**（B2）：「そのユーザーの札を、全部無効にする」部品が、書いてあるのに、どこからも呼ばれていなかった。文書にも「できる」と書いてあり、**前回のノートにも、私（Claude）が「想定」と書いた**。コードを検索（grep）するまで、気づかなかった。**文書の「できる」は、実際に動くかを、コードで確かめる**
- **文字数とバイト数**（B1）：パスワードの上限 72 は、BCrypt が 72「バイト」までしか扱えないため。英数字は 1 文字＝1 バイトだが、日本語は 1 文字＝3 バイト（UTF-8）。「72 文字まで」の検査だけでは、足りないかもしれない。**ただし、まだ確かめていない**（読んだだけ）。読んで見つけたことと、動かして確かめたことを、分けて書く
- **応答時間でも、情報がもれる**（B3）：メールが無いときだけ、BCrypt の計算（わざと遅い）を飛ばすと、応答が速い → 「そのメールは、登録されていない」と分かる。ただし、このアプリは、登録のときに「すでに使われています」と教えるので、もともと分かる。**どこまで守るかは、設計とセットで決める**

## 4. 覚えておくこと
- 指摘には、重大度（高・中・低）と、**推奨**と、**判断（ユーザーが決める）** の欄をつける
- 「既知（決めてある弱点）」も、記録する（例：localStorage）。あとで、決めた理由を思い出せる
- 次の点検では、前回の「判断」欄から、始める
