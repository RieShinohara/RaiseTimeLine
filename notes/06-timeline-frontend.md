# タイムラインの画面：無限スクロールと、モーダルの作り

2026-11-16。⑤-2（Issue #75）。投稿の API（[ノート 05](05-posts-api.md)）を、画面から使う。

## 2. 無限スクロールのしくみ
1. 一覧の一番下に、見えない目印（`<div ref=...>`）を置く
2. ブラウザの **IntersectionObserver**（「この要素が、画面に入ったか」を教えてくれる道具）で見張る
3. 目印が見えたら、次のページを読む。一番下に着く **200px 手前**で読み始めるので、止まらずに見える
4. **読み込み中・続きがない・失敗中は、見張らない**。終わるたびに、見張り直す（目印がまだ見えていれば、すぐ次を読む）

## 3. 気をつけたこと
- **同じ投稿を 2 回出さない。** 最初は、ページ番号方式で、「同じ `id` は足さない」処理で隠していた。2026-11-17 に、サーバー側を「**ここより古いもの**（`before`＝いちばん古い投稿の `id`）」方式に変えたので、ずれ自体が起きなくなり、隠す処理は、なくした（原因をなくすほうが、あとから隠すより確実）
- **続きの目印は、一覧の最後ではなく、「読んだ結果」から決める。** 一覧の最後を使うと、自分の投稿を足したり、一番古い投稿を消したりしたときに、目印が、ずれる。`useRef` に、読んだ最後の `id` を持つ
- **新着の基準も、日時から `id` に。** 日時の細かさ（マイクロ秒とミリ秒）を気にしなくてよくなった。投稿が 1 件もないときの基準は 0
- **二重に読まない。** `useRef` の「読み込み中」の印で、スクロールの連続や、画面の再描画で、同じ所を 2 回読まないようにした
- **失敗したら、ページを進めない。** 「もう一度」で、同じページをやり直せる
- **本文は、文字として表示する。** React は、`{post.body}` を HTML として解釈しない。`<img onerror=...>` と書かれても、ただの文字になる（XSS の対策。テストもある）
- **投稿に失敗しても、モーダルを閉じない。** 入力した文章が消えると、書き直しになる。理由を出して、そのまま、やり直せる
- **文字数の数え方は、サーバーと合わせる。** サーバー（Java）も、画面（JavaScript）も、`length` で数える（絵文字は 2 文字分）。ずれると、「画面では通るのに、サーバーで 400」が起きる
- **テストでは、IntersectionObserver の偽物を使う。** テスト用の仮想のブラウザ（jsdom）には、本物がない。「一番下に着いた」という合図を、自分で送る
- **既存のテストが、画面の変更で壊れた。** トップ画面が、開くと投稿を読むようになったため、「最初の通信は、ログアウト」と決め打ちしたテストが失敗した。URL ごとに、返事を分けるように直した
- **新しい部品（アイコン集 `@mui/icons-material`）は、最初は入れなかった。** 技術の追加は、ユーザーが決める。「＋」は文字で表した（⑤-3a で、ユーザーが入れると決めたので、アイコンにした）

## 4. 新着の確認（ポーリング）と、浮かぶバナー（⑤-3b）
**ポーリング**：画面が、一定の間隔で、サーバーに「新しいものはある？」と聞く方式（`setInterval`）。サーバーから画面へ、勝手に知らせる方式（WebSocket など）より、作りが簡単。代わりに、知らせが、最大 30 秒遅れる。

| ファイル | 役割 |
|---|---|
| `timeline/useNewPostsCount.ts` | 30 秒ごとに `new-count` を呼ぶ。見ていない間は止める。失敗は静かに待つ |
| `components/NewPostsBanner.tsx` | 画面の上に浮かぶバナー（`position: fixed`）。モーダルではない |
| `auth/jwt.ts` | アクセストークンの期限（`exp`）を、札の中身から読む |

気をつけたこと：
- **基準の日時は、「サーバーと同期したとき」の一番上の投稿。** 続きを読み込んだときや、自分が投稿したときに変えると、古い投稿まで「新着」になったり、他の人の新着が抜けたりする。**わざと壊して、テストが失敗することを確かめた**。最初は、続きを読み込む場面のテストがなく、壊しても通ってしまった（テストの穴）。穴に気づいて、足した
- **サーバーが返した日時の文字列を、そのまま渡す。** JavaScript の日付に変えると、細かい桁（マイクロ秒）が落ちて、一番上の投稿自体が、新着に数えられる
- **見ていない間は、聞かない。** `document.visibilityState` が `hidden` のとき（別のタブなど）は、無駄な通信なので、止める。戻ってきたら（`visibilitychange`）、すぐ 1 回聞く
- **「ログインなしでも使える API」と、期限切れの札の落とし穴。** 札が切れていても、その API は 401 を返さず、「札なし」として動く。すると、「自分の投稿を数えない」が効かない。**聞く前に、札の期限を自分で見て、切れていれば先に更新する**。札の中身（ペイロード）は、だれでも読める（秘密を入れていないため）。署名が本物かどうかは、サーバーの役目で、画面は、期限の見当をつけるだけ
- **古い結果を、使わない。** 基準が変わった（読み直した）あとに、前の基準での結果が戻ってきても、件数に使わない（件数は、基準が同じときの結果だけを、使う）
- **CI でだけ失敗する、不安定なテスト（flaky test）に出会った。** 「投稿が画面に出た直後に、目印の見張り（IntersectionObserver）の偽物を探す」テストが、手元では通り、CI（動きが遅い）で、たまに「見張りがまだない」で失敗した。読み込みが終わってから、見張りが作り直されるので、**出た直後は、まだない**ことがある。直し方は、`waitFor` で、見張りができるのを待ってから、合図を送ること。**手元で通っても、安心しない**（タイミングに頼ったテストは、遅い環境で壊れる）。CI のログを見て、原因を切り分けた
- **テストでは、時間を進める。** `vi.useFakeTimers()` と `advanceTimersByTimeAsync(30_000)` で、30 秒を一瞬で進める。本物の時計は、待たない

## 5. 編集と削除（⑤-3a）
- **編集は、投稿のモーダルを使い回す。** `PostComposerDialog` に `editing`（直す投稿）を渡すと、「編集」の形になる（タイトル・今の本文・「保存」）。部品を 2 つ作らずに済む。投稿ごとに `key` を変えて、前の入力が残らないようにした
- **削除は、確認のダイアログ（`DeletePostDialog`）。** 元に戻せない操作は、一度、確認を挟む。失敗したら閉じない
- **一覧の更新は、サーバーの返事で行う。** 編集は、サーバーが返した投稿（`updatedAt` つき）で置き換え、削除は、成功してから一覧から外す。画面だけ先に変えると、失敗したときに、嘘の表示になる
- **ボタンを出すのは、自分の投稿だけ（画面の親切）。** 本当の守りは、サーバーの 403（ノート 05）。わざと判定を壊して、テストが失敗することも確かめた
- **ボタンの名前は、「どの投稿の」まで入れる（品質チェック F7。2026-11-17）。** アイコンだけのボタンは、`aria-label` が、読み上げの名前になる。「編集、削除、編集、削除…」では、どの投稿か分からない。「サンプルの投稿「こんにちは…」を編集」のように、**投稿者と本文の頭（20 文字）**を入れた。テストでは、名前を、正規表現（`/を編集$/`）で探す（完全に同じ文字列を探すと、見つからなくなるため）
- **アイコンの名前に注意。** 線の細い版は `DeleteOutlined`（`DeleteOutline` という名前は、ない）。名前を間違えると、型の検査とテストが、すぐ教えてくれた
- **テストの落とし穴：モーダルが開いている間、背後の画面は、支援技術から隠される（`aria-hidden`）。** だから、`getByRole` では、背後の要素が見つからない（`hidden: true` で探す）。また、ダイアログは、閉じる動き（アニメーション）のあとで消えるので、`waitFor` で待つ
