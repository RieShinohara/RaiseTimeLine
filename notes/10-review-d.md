# 復習 D：品質チェックの道具と curl

2026-11-17。復習 A（[ノート 08](08-review-a.md)）・C（[ノート 09](09-review-c.md)）の続き。「curl は、品質チェックで出てきたと思う。道具には、複数あった。それぞれ何をしているのか」という、ユーザーの質問から始めた。

## 1. curl は、品質チェックの「道具」ではなく、「動かして確かめる手段」
**curl ＝ 画面を通さずに、API に、直接リクエストを送るコマンド。** 画面（ブラウザ）が、裏でやっている通信を、自分の手で 1 つだけ送る。

品質チェックでは、起動中のサーバーに、`curl` で、こう確かめた（[品質チェックの記録](../docs/quality-review.md)、[ノート 07](07-quality-check-2.md)）。
- 他人の投稿を編集 → **403** で断られるか
- 別のサイトからの通信（CORS）→ 許可のヘッダーが付かないか
- 設定が見える窓口（`/actuator/env`）→ **401** で断られるか

テストが緑でも、**今、動いている実物**が、同じ動きをするかは、別の確認。

### curl の読み方
```
curl -i http://localhost:8080/api/posts?size=2
```

| 部分 | 意味 |
|---|---|
| `curl` | 「この URL に、リクエストを送って」という道具 |
| `-i` | 返事の**ヘッダー**（状態コード 200 など）も、表示する |
| `http://localhost:8080/...` | 送り先。`localhost:8080` は、自分の PC のバックエンド |

```
curl -X PUT http://localhost:8080/api/posts/5 \
  -H "Authorization: Bearer ○○" \
  -H "Content-Type: application/json" \
  -d '{"body":"書き換え"}'
```

| 部分 | 意味 |
|---|---|
| `-X PUT` | PUT（書き換え）で送る。何も書かなければ GET（読むだけ） |
| `-H "Authorization: Bearer ○○"` | ヘッダーを付ける。ここに、アクセストークンを入れる（検問所が見る所） |
| `-H "Content-Type: application/json"` | 「中身は JSON」と伝える |
| `-d '{"body":"..."}'` | **本体（送る中身）**。画面の「保存」ボタンが、送るものと同じ |

### 注意
- **curl で見つけた問題は、あとで、自動のテストにするのが理想。** curl は、その場で打つ、手動の確認で、再実行されない。B8 や CORS は、見つけてから、テストに足した
- Git Bash から、日本語を送ると、文字化けすることがある（登録の確認で、表示名を英数字にした）

## 2. 品質チェックの道具

### バックエンド（`.\gradlew.bat check` で、まとめて動く）
| 道具 | たとえ | 何をする |
|---|---|---|
| JUnit ＋ Testcontainers | 試運転 | テストを動かす。本物の PostgreSQL を、使い捨てで起動して、DB も含めて確かめる |
| Checkstyle | 国語の先生（書式） | **書き方の決まり**（インデント、名前の付け方、不要な import）。違反が 1 つでもあれば、失敗にしている |
| SpotBugs | 校閲者（バグの芽） | バグになりやすい書き方を、動かさずに探す（`null` の見落とし、閉じ忘れ、半端なオブジェクトなど） |
| JaCoCo | 試運転の記録係 | テストが、コードのどこを通ったか（カバレッジ）を測る。今は「測るだけ」 |
| ArchUnit | 設計図の見張り番 | 「Controller は Mapper を直接呼ばない」など、**層の約束が、守られているか**を、テストとして確かめる |

### フロントエンド
| 道具 | たとえ | 何をする |
|---|---|---|
| oxlint（`npm run lint`） | 校閲者 | 使っていない変数、危ない書き方を探す。`--deny-warnings` で、警告も失敗 |
| Prettier（`format:check`） | 整える係 | 見た目の整形（改行、空白、引用符）をそろえる |
| TypeScript（`tsc -b`。`build` の中） | 型の検査官 | 型の食い違い（数字のはずが文字、など）を、動かす前に見つける |
| Vitest ＋ Testing Library（`npm test`） | 試運転 | 画面の部品を、仮の環境で動かし、ボタンを押す・文字が出るなどを確かめる |
| Vite のビルド（`npm run build`） | 製品の組み立て | 本番用に、まとめて作れるか |

### CI（GitHub Actions）
上の道具を、**PR のたびに、自動で、クリーンな環境で動かす**仕組み。「手元では通ったのに、CI では落ちる」（不安定なテスト）も、ここで見つかる。

## 3. 3 枚の網
| 点検 | 見つけるもの | 見つけられないもの |
|---|---|---|
| 書式・バグの芽・型（Checkstyle、SpotBugs、oxlint、tsc） | 書き方の乱れ、危ない書き方、型の食い違い | 「動きが正しいか」 |
| 自動テスト（JUnit、Vitest） | 決めた動きと違う所 | **テストに書いていない動き** |
| 実物を、手で動かす（curl、ブラウザ） | **今の実物が、どう動くか** | 毎回は動かせない |

重ねるほど、すり抜ける物が減る。例：`/error` が 401 に化けた問題は、テストでは気づけず、curl で見つけた（[ノート 03](03-auth-implementation.md)）。

## 4. 問題と答え
**D-1. 「テストが緑」「Checkstyle が緑」「curl で期待どおり」の 3 つを、全部確かめるのは、なぜ？**
- 自分の答え：テストは、期待どおりに動くかを確かめる。Checkstyle は、書き方・型の違いを見つけて、バグを防ぐ。curl は、実際にサーバーが動くかを確かめる。目的が違うので、1 つでは、カバーしきれない
- 補足・訂正：結論は正解。**Checkstyle が見るのは書き方の決まり**で、型の違いを見つけるのは、コンパイラ（Java）と `tsc`（TypeScript）。バグの芽は、SpotBugs と oxlint。道具ごとに、役が違う。また、**curl は、自動のテストではなく、手動の確認**

**D-2. `curl -i -X DELETE http://localhost:8080/api/posts/5` を、日本語にすると？ 返る状態コードは？**
- 自分の答え：返事のヘッダーも表示する。自分の PC のバックエンドの、投稿 5 を、DELETE で送る。状態コードは 401
- 補足：正解。札がない → `userId` は `null` → ログインが必要な URL は 401。「新規投稿 5」ではなく、**「`id` が 5 の投稿」**（すでにある投稿を消す依頼）

### 401 と 403
| コード | 意味 | たとえ |
|---|---|---|
| 401 | あなたが**誰か、分からない**（札がない・偽物・期限切れ） | 会員証を見せていない |
| 403 | 誰かは分かるが、**してはいけない**（他人の投稿を編集） | 会員証はあるが、その部屋には入れない |

## 5. 学んだこと
- 品質チェックの道具は、**「読んで点検」「動かして点検」「実物を動かして確かめる」**の 3 つに分かれ、役が違う。どれが何を見つけるかを、言えるようにする
- **道具が緑でも、「本当に何かを調べているか」を疑う**（CLAUDE.md の 7。わざと壊して、失敗するかを確かめる）
- 3 つの網は、粗さと形が違う。重ねるほど、すり抜けが減る
