# 復習 A：全体の地図と認証

2026-11-17。コメント・いいねの実装の前に、これまでの内容を、**自分の言葉で答える**形で復習した。読むだけでは気づけない「ずれ」が、書くと見える。

## 全体の地図
```
ブラウザ（React の画面）
   │ ① GET /api/posts?size=20
   ▼
バックエンド（Spring Boot）
   Controller（ウェイター）→ Service（料理長）→ Mapper（倉庫番）
   │ ② SQL
   ▼
PostgreSQL（倉庫。Docker の中）
```

## 問題と答え

**A-1. 画面が、DB に直接つながらず、バックエンドを挟むのは、なぜ？**
- 自分の答え：直接だと、意図しない操作や悪意のある操作を、見抜けない。仕組みで守れなくなる
- 補足：**画面のコードは、使う人のブラウザに全部ダウンロードされる**ので、誰でも読める。DB のパスワードを画面に持たせると、公開したのと同じになる

**A-2. Controller・Service・Mapper に分けるのは、なぜ？**
- 自分の答え：直したい部分だけを変えればよく、アップデートしやすい
- 補足：例）280 文字を変える → 入力の条件だけ。DB を変える → Mapper だけ。**層の約束が守られているかは、ArchUnit のテストで、機械が確かめている**

**A-3. 画面でボタンを隠しているのに、サーバーでも「自分の投稿か」を確かめるのは、なぜ？**
- 自分の答え：画面を通らない悪意のあるアクセスがあるから。両方で確認して、データを守る
- 訂正：「悪意のあるサイトから PC に侵入」は、別の攻撃の話。本当の理由は、**画面のコードは、使う人の手元で動くので、書き換えられるし、使わなくてもよい**から。`curl` で、画面を通さずに API を直接叩ける
- まとめ：**画面のチェックは、親切のため。サーバーのチェックは、守るため**

**A-4. サーバーは、どうやって「ログインしている人か」を知る？**
- 自分の答え：サーバーだけが持つ秘密の鍵で、ヘッダーとペイロードから署名を計算し、届いた署名と照らして、一致すれば本物
- 訂正：最初は「メールアドレスから計算」と書いていた。**計算に使うのは、秘密の鍵（`JWT_SECRET`）**。メールアドレスは使わない。ペイロードに入っているのも、ユーザー ID と期限
- 補足：ペイロードを書き換えると、署名が合わなくなる。鍵を知らないので、作り直せない。**一致して分かるのは「サーバーが発行した本物」ということまで**。「この操作をしてよいか」は、Service が別に判断する

流れ：
1. 画面が `Authorization: Bearer ○○` を付けて送る
2. `JwtAuthenticationFilter` が、署名を計算し直して、本物か・期限内かを確かめる
3. 大丈夫なら、ユーザー ID を記録 → Controller の `@AuthenticationPrincipal userId` に入る
4. 札がない・偽物なら `userId` は `null`。ログインが必要な URL は、401

**A-5. アクセストークンは 15 分で切れるのに、ログインし直さなくてよいのは、なぜ？**
- 自分の答え：リフレッシュトークンが 7 日あり、DB の情報と一致すれば、継続できる
- 補足：401 → `/api/auth/refresh` → 新しいアクセストークン → **同じ操作をやり直す**（`api/http.ts`）。「一致」の中身は、**DB に発行の記録がある・`revoked` でない・期限内**の 3 つ

## 宿題（答えた）
> アクセストークンの期限を 7 日にすれば、リフレッシュトークンは要らないのでは？ なぜ 2 種類にしているのか？

- 自分の答え：アクセストークンを 7 日にすると、危険な時間が長くなり、仕組み上、すぐには取り消せない。リフレッシュトークンは、ただの文字列で DB にあるので、すぐ取り消せる。期限が長くても、リスクが低い
- 補足：取り消しは、削除ではなく **`revoked = true` の印**（記録が残る）。もうひとつの理由は、**札が外に出る回数**。アクセストークンは API のたびに、リフレッシュトークンは `/api/auth/refresh` のときだけ送る。外に出る回数が少ないほど、盗まれる機会も少ない
- まとめ：**短命でよく使う札と、長命でめったに使わない札に、役割を分けている**
