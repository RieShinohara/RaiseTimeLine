## 2. N+1 問題を、数字で見た
一覧（20 件）に、「いいね数」と「自分が押したか」を足す。

| 作り方 | SQL の回数（20 件） | 5 件 | 100 件 |
|---|---|---|---|
| **素直な作り方**（1 件ずつ聞く） | 1 + 20 + 20 = **41 回** | 11 回 | 201 回 |
| **まとめて聞く** | **3 回** | 3 回 | 3 回 |

- 自分の予想（41 回）が、**実際のテストの数字と一致した**
- 素直な作り方は、件数に**比例して増える**。まとめて聞く作り方は、**件数によらず一定**
- ログインなしは、「押したか」を聞かないので、2 回（一定）

### まとめて聞く、とは
```sql
-- いいね数：20 件ぶんを、GROUP BY で、投稿ごとに数える（1 回）
SELECT post_id, COUNT(*) FROM post_likes WHERE post_id IN (…20 個の id…) GROUP BY post_id

-- 自分が押したもの：20 件ぶんを、IN で、まとめて調べる（1 回）
SELECT post_id FROM post_likes WHERE user_id = 自分 AND post_id IN (…20 個の id…)
```
- `GROUP BY`：「同じ `post_id` の行を、1 つの組にして、組ごとに数える」
- `IN (…)`：「この番号の、どれかに当てはまる行」
- **まとめた結果は、Java 側で、投稿に割り振る。** `Map<投稿の id, 数>` を作り、`getOrDefault(id, 0)` で引く。**いいねが 0 件の投稿は、`GROUP BY` の結果に出てこない**ので、「ない → 0」にする（ここを忘れると、数が空になる）

### 落とし穴
- **`IN ()`（空の一覧）は、SQL の間違い**。投稿が 0 件のときは、聞く前に、空かどうかを確かめて、聞かない（Service で確かめる）
- 値は、今回も `#{}`（`<foreach>` の中でも）。`${}` は使わない

## 3. SQL の回数を、テストで数える
- 「N+1 になっていないか」は、**画面を見ても、結果の正しさのテストを見ても、分からない**（どちらも、結果は同じ）。**SQL の回数を数える**ことで、初めて分かる
- 方法：MyBatis に、**見張り（`Interceptor`）**を入れる。SELECT が実行されるたびに、数を 1 増やす。**テストにだけ入れる**（本番のコードには入れない）。新しい部品（ライブラリ）は、足していない
- テストは、「20 件でも 5 件でも、3 回」と確かめる（**件数を変えても、回数が同じ**ことが、N+1 でない証拠）
- **先に素直な作り方で作り、回数を数えて「41 回」を確かめてから、直した。** コミットも 3 つに分けた（表と API → 素直な一覧 → まとめて聞く形）。直す前と後が、差分で見える
- **わざと壊して、テストが失敗することも確かめた**：①二重押しの守り（`ON CONFLICT DO NOTHING`）を外すと、「何回押しても 1 回分」のテストだけが失敗。②「数」を、いつも 0 にすると、「数が正しい」のテストだけが失敗

## 4. 二重のいいねを防ぐ
- **主キー `(post_id, user_id)`**：2 つの番号の**組み合わせ**が固有。`user_id` だけ、`post_id` だけが同じなのは、OK（同じ人は、たくさんの投稿に、いいねできる。同じ投稿には、たくさんの人が、いいねできる）。**両方が同じ行だけ、2 つ作れない**
- `INSERT ... ON CONFLICT DO NOTHING`：「組み合わせがぶつかったら、何もしない」。**確認と追加を、1 つの SQL で行う**ので、同時に 2 回押されても、行は 1 つ。「確かめてから、入れる」の 2 段階だと、間に割り込まれる（[復習 C](09-review-c.md) の、更新の「隙間」と同じ考え方）
- **何回押しても、結果は同じ**（エラーにしない）。取り消しも同じ。画面の、連打や、通信のやり直しに強い

## 6. 気をつけたこと

- **投稿を消すと、いいねも消える。** 表の外部キーに `ON DELETE CASCADE`。テストで確かめた（アプリのコードで消す処理は、書いていない）
