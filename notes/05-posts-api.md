# 投稿の API：設計の読み方と、気をつけたこと

2026-11-16。講義 28 の API 設計にそろえて、投稿のバックエンド（⑤-1）を作った。

## 1. API 設計の表の読み方
| Method | Path | 意味 |
|---|---|---|
| GET | `/api/posts?before={id}&size=20` | 取得（データを読むだけ）。`?` のあとは、条件（クエリパラメータ）。`before` は「この投稿より古いもの」（2026-11-17 に、`page=0` から変更。5 を見る） |
| POST | `/api/posts` | 新しく作る → **201**（作った） |
| PUT | `/api/posts/{id}` | 既存の 1 件を、書き換える。`{id}` は、投稿の番号 |
| DELETE | `/api/posts/{id}` | 消す → **204**（成功。返す中身はない） |

- Method は「何をしたいか」、Path は「何に対して」。同じ Path でも、Method が違えば、別の操作
- 状態コード：200（成功）、201（作った）、204（成功・中身なし）、400（入力が変）、401（ログインしていない）、**403（ログインしているが、権限がない）**、404（見つからない）。401 と 403 の違いが大事：他人の投稿を編集しようとしたら 403

## 2. ファイルの役割（認証と同じ作り）
| ファイル | 役割 |
|---|---|
| `PostController` | 窓口。URL と Method を受けて、サービスに渡す |
| `PostService` | 決まりごと（本人だけ、280 文字、見つからない）を判断する |
| `PostMapper` | SQL を書く場所（MyBatis） |
| `Post`・`PostDtos` | DB の 1 行の形、API の入力・出力の形 |
| `V2__create_posts.sql` | `posts` 表を作る（Flyway） |

## 3. 気をつけたこと
- **「本人だけ」は、サーバーで確かめる。** 画面で編集ボタンを隠しても、API を直接呼ばれたら通る。わざと検査を外して、テストが失敗することも確かめた
- **N+1 を避ける。** 投稿 20 件ごとに、投稿者を 1 回ずつ調べると、SQL が 21 回になる。`JOIN` で、投稿と投稿者を、1 回の SQL で読んだ（⑥では、いいね数・コメント数でも、同じ問題が出る）
- **ページ番号方式の弱点（最初の版）。** 「21〜40 件目」と指定すると、新しい投稿が入ったときに、全体がずれて、同じ投稿が 2 回出る。投稿が消えると、1 件飛ばされる（取りこぼし）。最初は、先生の設計にそろえて、画面側で重複だけ隠していた
- **カーソル方式に変えた（2026-11-17。Issue #87）。** 「**この投稿（id）より古いもの**を 20 件」と指定する。`id` は、投稿のたびに増える番号なので、「栞（しおり）」のように、新しい投稿が入っても、消えても、ずれない。しおりを挟んだページから、続きを読むイメージ。`SELECT ... WHERE id < :before ORDER BY id DESC LIMIT 21`（1 件多く読んで、続きがあるか＝`hasNext` を知る）。**主キーの索引がそのまま効く**ので、日時の索引は、V3 で消した
- **新着の確認も、id で。** `GET /api/posts/new-count?after={id}` ＝「この id より大きい投稿の件数」。**日時の細かさ（DB は 100 万分の 1 秒、JavaScript は 1000 分の 1 秒。変換すると、一番上の投稿自体が新着に数えられた）の問題が、なくなった**。整数の比較だけなので、変換のずれが、起きない
- **テストで、「途中で投稿が入り、読んだ投稿が消えても、ずれない」ことを確かめた**
- **既存のテストが、仕様の変更で壊れた。** 「ログインが要る API」の例に、`GET /api/posts` を使っていたが、タイムラインは、ログインなしで見られる仕様なので、失敗した。テストが「今の仕様」を見張っている証拠。直すのは、テストの期待（ログインが要る `POST /api/posts` に変えた）
- **`size` に上限（50）をつけた。** 大きな数を指定されて、サーバーが重くなるのを防ぐ

## 4. 品質チェックの指摘を直した（2026-11-17。Issue #99）
- **「確認してから更新」を、1 回の SQL にした（B8）。** 以前は、①本人か調べる → ②更新、の 2 回。その間に投稿が消されると、②のあとの読み直しが空になって、500 になりえた。今は `UPDATE … WHERE id = ? AND user_id = ?`。**条件が合わなければ 0 件**になるので、「なかった」と分かり、404 を返す。①の確認は、「他人の投稿＝403」と「ない＝404」を分けるために、残している
- **本文の前後の空白を取る（B9）。** `PostRequest` の中（record の「コンパクトコンストラクタ」）で `strip()` する。**検査（`@NotBlank`・`@Size`）は、このあとに働く**ので、「前後に空白が付いて 281 文字」でも、取った後の 280 文字なら通る。`trim()` でなく `strip()` を使う理由：`trim()` は半角の空白だけ、`strip()` は全角の空白も取る
- **層の向きを、テストで見張る（B5）。** ArchUnit で、「Controller は Mapper を直接呼ばない」「Mapper は Service・Controller を呼ばない」「Service は Controller を呼ばない」を検査。`Controller` に `Mapper` を持たせると、狙いどおり失敗することも確かめた。**「0 件を調べて成功」を避けるため、クラスが読み込めていること自体も、テストした**
- **エラーの順（B6）。** 入力の誤りが複数あるとき、DTO に書いた項目の順（メール → パスワード → ユーザー名 → 表示名）で、先頭の 1 件を返す
- **つまずき：最初のテストは、新旧の違いを確かめられなかった。** わざと古いコードに戻しても、テストが通ってしまった。誤りの組み合わせが、たまたま「日本語の文字順」と「項目の順」で同じ結果になっていたため。**「古いコードで失敗する」ことを確かめて、初めて、テストが働いていると言える**。メールとパスワードの両方が誤りの組み合わせに直して、古いコードで失敗することを確認した
- **つまずき：わざと壊す確認で、PowerShell を使うと、日本語のファイルが壊れた**（コンパイルエラーを、「テストの失敗」と読み違えるところだった）。書き換えは、Edit ツールで。**失敗の中身（コンパイルか、テストか）を、読む**
