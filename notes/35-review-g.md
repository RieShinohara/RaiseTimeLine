## 復習 1：認証の 3 つのファイル（受付のたとえ）

| ファイル | たとえ | 仕事 |
|---|---|---|
| JwtService | 札の発行所・鑑定士 | 札を作る（30 行目）。札が本物かを調べる（42 行目。だめなら空を返す） |

- 流れ：リクエスト → Filter（スタンプ）→ ルール表 → Controller → Service。
- 書いていない道は、全部スタンプが必要（54 行目の `anyRequest().authenticated()`）。安全側に倒してある。

### 自分の答え（3 問）と補足
1. 期限切れの札で `POST /api/posts` → 「Filter でスタンプは押されず、SecurityConfig で 401」。**正解。**
2. 同じ札で `GET /api/posts` → 「permitAll なので通過する」。**正解。** 期限切れの札は、エラーでなく「札が無いのと同じ扱い」になる。
3. 札の ID を書き換えたら → 「署名が正しくないと判断される」。**結論は正解。** 実験で確かめた（下の復習 2）。

| 札の状態 | スタンプ | permitAll の道 | authenticated の道 |
|---|---|---|---|
| 本物・期限内 | 押す | 通れる | 通れる（→ Service で権利を確認） |

## 復習 2：実験（わざと札を壊す）

手元の DB に、架空のユーザーを作って、札を書き換えて送った。

| 実験 | 結果 | 意味 |
|---|---|---|
| 札なしで投稿 | **401** | 札が無い |
| 署名の中ほどの 1 文字を変える | **401** | 偽物。スタンプは押されない |
| 中身の ID を別の人に書き換える（署名はそのまま） | **401** | **なりすましはできない** |
| 署名の**最後の 1 文字**を、余りの部分だけ変える | **201（通る）** | 偽造ではない（下） |
| 本物の札で、自分の投稿を削除 | **204** | 本人は消せる |
| 札なしで、他人の投稿を削除 | **401** | 誰か分からない |
| 他人の札で、他人の投稿を削除・編集 | **403** | 誰かは分かるが、許されていない |

### 「1 文字変えたのに通った」の原因
- 最初の実験で、最後の 1 文字を変えた札が **201 で通って**、驚いた。偽造が成功したのではないかと疑って、調べた。
- 署名は 86 文字（64 バイト）。1 文字は 6 ビットだが、**最後の 1 文字だけは、4 ビットしか使わず、2 ビットが余り**。余りの部分だけを変えると、**署名のバイト列は同じ**になる（実験で、`同じ？ True`、結果 201）。使われている 4 ビットを変えると、バイト列が変わって 401（`同じ？ False`）。
- つまり、**元の札と、まったく同じ意味の札**ができただけ。ID も期限も変わらない。元の札でできることしかできない。
- 問題にならない理由（ユーザーの答え「ID と有効期限が同じで、本人のものと分かる」は正しい）。**注意点**：もし「札の文字列そのもの」を目印に使う仕組み（ログアウトした札の文字列を覚えて拒否する、など）があれば、見た目の違う同じ札で、すり抜けられる。このアプリの札は、覚える方式ではないので、関係ない。
- **訂正（Claude Code の言い過ぎ）**：「札を 1 文字変えると偽物になる」と説明したが、正確には「**署名の中身が変わると**偽物になる」。実験をしないと、気づけなかった。

### 実験のやり方のつまずき
- **最初の実験は、設計が悪かった**（最後の 1 文字を変えた）。「成功」を疑って、原因の仮説を立てて、**仮説を確かめる実験**（余りだけ変える／中身を変える）を足した。CLAUDE.md の 7（道具の成功を疑って確かめる）の例。
- Windows PowerShell 5.1 は、BOM の無い UTF-8 のスクリプトを、文字化けして読む（日本語を書いた `.ps1` が構文エラーになった）。先頭に BOM を付けて直した。
- 札の中身（`sub`・`email`・`iat`・`exp`）は、暗号ではなく、base64 で読める。**だから秘密は入れない**（[JwtService](../backend/src/main/java/com/example/raisetimeline/auth/JwtService.java) の 17 行目のコメントにも、中身は ID とメールだけと書いてある）。署名があるのは「隠す」ためでなく「書き換えを見つける」ため。

## 復習 3：403 を返す判断（Service）
- 「403 は Service が、札の userId と投稿の userId を確認」→ **正解。**
- 実物：[PostService の `findOwned`](../backend/src/main/java/com/example/raisetimeline/post/PostService.java#L157)。`post.getUserId().equals(userId)` を見て、違えば 403（「他の人の投稿は、編集・削除できません」）。
- 補足：
  - 札の持ち主の ID は、Filter が札から取り出し、Controller が `@AuthenticationPrincipal` で受け取って、Service に渡す。**画面から送られた ID は使わない**。
  - 順番は「あるか（無ければ 404）→ 本人か（違えば 403）」。
  - Mapper の SQL にも「本人の条件」がある（`deleteById(id, userId)`）。確認と削除の間に何かが起きても、他人の投稿は消せない。**二重の守り**。

## 復習 4：札の 2 種類（アクセストークンとリフレッシュトークン）

### 問題と自分の答え
1. 「なぜ短い期限か」→「壊れたり流出したりしても、短期間で期限切れになり、攻撃のリスクをおさえられるから」。**正解。**
2. 「期限が短いと、何度もログインし直すことにならないか。どうしている？」→「アクセストークンは 15 分と短いが、7 日期限のリフレッシュトークンがあり、それが期限内なら、アクセストークンを再発行してくれる。リフレッシュトークンはハッシュ化して DB に保管される」。**仕組みは正解。ハッシュ化の所だけ、違った**（下）。

### 2 種類の違い

| | アクセストークン | リフレッシュトークン |
|---|---|---|
| 期限 | 15 分（`access-expiration-ms: 900000`） | 7 日（`refresh-expiration-days: 7`）。[application.yml](../backend/src/main/resources/application.yml#L28-L29) |
| 形 | JWT（署名つき。中身が読める） | ランダムな文字列（UUID。36 文字） |
| サーバーが覚える？ | **覚えない**（署名で本物か調べる） | **DB に覚える**（`refresh_tokens` 表） |
| 無効にできる？ | できない（期限切れを待つ） | **できる**（`revoked = TRUE`） |
| 使う場所 | 毎回の API（`Authorization: Bearer`） | 15 分ごとの更新と、ログアウトだけ |

- 更新の流れ：[AuthService.refresh](../backend/src/main/java/com/example/raisetimeline/auth/AuthService.java#L83)。リフレッシュの札が、**ある・無効でない・期限内**なら、新しいアクセストークンを出す。どれかが違えば 401。
- ログアウト：[AuthService.logout](../backend/src/main/java/com/example/raisetimeline/auth/AuthService.java#L97)。リフレッシュの札を `revoked = TRUE` にするだけ。何度呼んでも、同じ結果（204）。

### 訂正：リフレッシュトークンは、ハッシュ化していない
- 保存は、ランダムな UUID を**そのまま**（AuthService 76 行目）。照合も、そのまま（[RefreshTokenMapper.xml](../backend/src/main/resources/mapper/RefreshTokenMapper.xml#L12) の `WHERE token = #{token}`）。
- ハッシュ化しているのは、**パスワード**（AuthService 56 行目。BCrypt）。ここが混ざった。
- 理由の違い：パスワードは、人が決めた推測されやすい文字列なので、DB が漏れても読めないようにハッシュ化する。リフレッシュの札は、サーバーが作る推測できないランダムな文字列だが、**DB が漏れると、そのまま使えてしまう**。
- **選択肢（Claude Code の提案。要件にない。決めるのはユーザー）**：リフレッシュの札も、SHA-256 などでハッシュ化して保存する。今は、やっていない。やるかどうかは、まだ決めていない（課題やデプロイ前に、見直す候補）。

### 実験：ログアウトのあと（ユーザーの予想は 2 問とも正解）
| 操作 | 結果 | 意味 |
|---|---|---|
| ログイン中に、アクセストークンで投稿 | 201 | 使える |
| ログイン中に、リフレッシュトークンで更新 | 200 | 新しいアクセストークンが出る |
| ログアウト | 204 | リフレッシュの札を `revoked = TRUE` にした |
| **ログアウト後に、同じアクセストークンで投稿** | **201（成功）** | 覚えていないので、期限まで（最大 15 分）有効 |
| **ログアウト後に、同じリフレッシュトークンで更新** | **401** | `revoked` が TRUE なので断られる |
| もう一度ログアウト | 204 | 何度呼んでも同じ |

- **「覚えない方式」の弱み**：ログアウトしても、すでに出したアクセストークンは、最大 15 分は使える。短い期限で、弱みを小さくしている。
- 復習 2 で「札の文字列の見た目が違っても問題ない」と言えたのも、アクセストークンを覚えていないから。

## 復習 5：画面側の札の自動更新

実物は、[http.ts](../frontend/src/api/http.ts)（通信の窓口）・[tokenStorage.ts](../frontend/src/auth/tokenStorage.ts)（札を入れる財布。`localStorage`）・[AuthContext.tsx](../frontend/src/auth/AuthContext.tsx)（今ログイン中の人）。

### 役割分担：止めるのはサーバー、やり直すのは画面
- サーバー：札を調べる、止める（401・403）、新しい札を出す。
- 画面：札を財布に持つ、付ける、**401 を見て、更新して、同じ操作をやり直す**。

### 期限切れのアクセストークンで投稿したときの流れ

| 順 | 誰が | 何をする |
|---|---|---|
| ① | 画面（`send`） | 期限切れの札を付けて、`POST /api/posts` を送る |
| ② | サーバー（SecurityConfig） | スタンプが無いので、**401 を返す**。投稿の処理は、まだ何も始まっていない |
| ③ | 画面（`apiFetch`） | 401 を見て、`/api/auth/refresh` を呼ぶ（リフレッシュの札を送る） |
| ④ | サーバー（AuthService.refresh） | 札を確かめて、新しいアクセストークンを返す |
| ⑤ | 画面（`tryRefresh`） | 新しいアクセストークンを、財布に保存する |
| ⑥ | 画面（`apiFetch` の最後） | **同じ `POST /api/posts` を、もう一度送る** |
| ⑦ | サーバー | Controller → Service → Mapper → DB（INSERT）→ DTO に入れて返す |
| ⑧ | 画面 | 結果を受け取って、新しい投稿として表示する |

- 利用者のボタンは 1 回だが、サーバーには投稿のリクエストが **2 回届く**。最初の 1 回は 401 で止まり、投稿は何も動かない。**投稿が実行されるのは、⑦の 1 回だけ**なので、二重投稿にならない。

### 自分の答え（3 問）と補足
1. 流れの答えは、**⑦（INSERT して DTO で返す）は正しい**が、**更新をするのは、サーバーでなく画面**（サーバーの入口は 401 を返すだけ）。また、「レスポンスの札の期限を確認する」処理は無い。画面が期限を調べるのは、`refreshIfExpired` だけ（次の項）。
2. リフレッシュの札も期限切れ → 「財布が空になり、ログインが切れる」は**正解**。細かくは、`clearSession` で財布を空にして、`authLostHandler` → `setUser(null)` で、**ログアウトの状態に切り替わる**。「ログインが切れた」というメッセージが出るかは、ページの作りしだい（未確認）。
3. 「ログアウトは財布の札を削除する」は**半分正解**。その前に、**サーバーの `/api/auth/logout` も呼ぶ**（リフレッシュの札を `revoked = TRUE` にする）。成功しても失敗しても（`finally`）、財布は空にする。通信できなくても、この端末では、必ずログアウトできる（ただし、そのときサーバー側では、無効にできていない）。

### 工夫が 3 つ
1. **同時に何本も 401 が来ても、更新は 1 回だけ**（`refreshing` に、進行中の更新を入れて、みんなが同じ更新を待つ）。タイムラインは、複数の API を同時に呼ぶ。別々に更新すると、同じリフレッシュの札を何度も使ってしまう。
2. **期限を先に調べる `refreshIfExpired`**：ログインなしでも使える API（新着の件数など）は、期限切れの札を「札なし」として扱うので、**401 が返らない**＝更新のきっかけが来ない。呼ぶ前に、画面が期限を見て、先に更新する。復習 1 の「期限切れでも `permitAll` の道は通れる」と、同じ理由。
3. **通信の失敗と、札の無効を区別する**：電波が悪いだけなら、ログアウトさせない（`'error'`）。札が無効なら、ログアウトの状態にする（`'invalid'`）。

### 話の整理
- 札の置き場所は、`localStorage`（財布）。ブラウザの保存場所の選択は、[ノート 01](01-auth-basics.md) の「札の保存場所」に書いてある。

## 守る場所の整理

| 守る場所 | 何を見る | 失敗すると |
|---|---|---|
| ① SecurityConfig（ルール表） | スタンプ（札が本物か）があるか | 401 |
| ② Controller | 形（空でない、280 文字まで） | 400 |
| ③ Service | 札の持ち主 ＝ 投稿の持ち主か | 403（投稿が無ければ 404） |
| ④ Mapper の SQL | 「本人の条件」も入れる | 0 件 |
| ⑤ DB | 主キー・外部キー・CHECK | エラー |

## 振り返り（前日の復習 F への返事）
- 主キー（重複を防ぐ）・外部キー（存在しない相手を指さない）は、正しく言えていた。**CHECK（値の範囲を守る。例：投稿は 280 文字まで）が抜けていた**ので足した。
- 認証の場所は、1 か所でなく、SecurityConfig（ルール表）と Filter（スタンプ）と JwtService（札の発行・鑑定）の 3 か所。
