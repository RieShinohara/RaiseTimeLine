# 品質チェック（2回目）で学んだこと

2026-11-17。投稿とタイムラインができた節目で、2 回目の点検をした。結果は [docs/quality-review.md](../docs/quality-review.md)。1 回目の学びは [04](04-quality-check-1.md)。

## 1. 今回の結果
- 道具は、全部成功（テスト：サーバー 24 件＋画面 63 件、lint 0 件、リンク切れ 0 件）。それでも、**読んで見つかったことが 5 件**あった（B8〜B10、F7・F8）。さらに、CI で**テストが 1 件、たまに失敗**することも見つかった（F9）。1 回目の 13 件から、新しい機能の分だけ、少なくなった
- カバレッジ（テストが通ったコードの割合）は、命令 94% → 97% に上がった。ただし、**数字が高い＝問題がない、ではない**（B8 のような「ごくまれな競合」は、数字に出ない）

## 2. 点検で分かった、おもしろい例
- **「確かめてから、書き換える」の間に、すきまがある**（B8。**確認と実行の間の競合**）
  - いまの編集：①「この投稿は、あなたのものですか？」と調べる → ②書き換える。この 2 つが、別の SQL
  - たとえ：**銀行の窓口で、「本人確認 OK」のあと、書類を出す前に、別の窓口で、その口座が閉じられた**。①は通ったのに、②のときには、もうない
  - 直し方の考え方：確認を、書き換えの**条件の中に入れる**（`UPDATE … WHERE id = ? AND user_id = ?`）。「0 件しか変わらなかった」で、「なかった」と分かる。確認と実行が、1 回の SQL になる
  - **ただし、読んだだけで、再現していない**。まれな競合は、普通に動かすと、起きない。記録では「読んで見つけた」と書き分けた
- **動かして確かめられることは、動かす**：「他の人の投稿を編集」「別のサイトからの通信（CORS）」「設定が見える窓口（`/actuator/env`）」は、`curl` で実際に送って、断られることを確かめた（403・許可のヘッダーなし・401）。テストが緑でも、**今の実物が、同じ動きをするか**は、別の確認
- **「空白だけ」は断るのに、「前後の空白」は、そのまま保存**（B9）。`@NotBlank` は、空白だけの本文を断る。でも、`"  spaced  "` は、通って、そのまま保存される。**検査の条件は、「何を断るか」だけでなく、「何を通すか」も、確かめる**
- **ボタンの名前が、全部同じ**（F7）。画面では、投稿の横にあるから分かる。でも、スクリーンリーダー（読み上げ）は、ボタンの名前だけを順に読む。「編集、削除、編集、削除…」では、どの投稿か分からない。**目で見える文脈は、読み上げには、伝わらない**

- **たまに失敗するテスト**（F9。**この PR の CI で、実際に起きた**）：「30 秒より 1 ミリ秒だけ手前では、まだ確認しない」を確かめるテストが、遅い環境で落ちた。テストの偽の時計は、本物の時計も少し進む設定で、**余裕が 1 ミリ秒しかなかった**ため。たとえ：「ぴったり 30 分前に着く」を約束すると、電車が 1 分遅れただけで、破れる。**余裕を持たせる**（29 秒で確かめる）と、安定する。**手元で通った＝いつも通る、ではない**（再実行で緑になっても、原因を調べて記録する。「たまたま通った」を、解決とは呼ばない）

## 3. N+1 の予行（次のコメント・いいねのため）
- **今の一覧は、N+1 になっていない**。投稿と投稿者を、1 回の `JOIN` で読んでいるため（SQL は 1 回）
- コメント数・いいね数を足すとき、投稿 1 件ごとに数えると、**1 回 ＋ 20 回 ＋ 20 回**になる。解決策：**投稿の id を、まとめて渡して、数をまとめて数える**（`GROUP BY`）。実装のときに、SQL の回数を数えるテストで、確かめる

## 4. 覚えておくこと
- 点検の順番：①前回の「判断」欄を埋める → ②読む → ③動かして確かめる → ④記録（読んだことと、動かしたことを分ける）
- **道具の「成功」を疑う**：lint とリンク確認の両方で、わざと壊して、検出されることを確かめた
- 指摘は、直す前に、**直す・今は直さない・作る機能のときに**を、ユーザーと決める（今回は、案を先に出して、決めてもらった）
