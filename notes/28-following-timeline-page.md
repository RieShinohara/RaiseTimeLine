# 「フォロー中」タイムラインの画面

2026-11-22。Issue #155。API（ノート 27）の続き。トップ画面に、「全体」と「フォロー中」のタブを足した。

## 1. 作りの考え方：一覧の部品を、2 回使い回す
トップ画面を、2 つに分けた。

| 部品 | 役目 |
|---|---|
| `HomePage` | タブだけを持つ（どちらが選ばれているか） |
| `Timeline`（`kind` を受け取る） | 一覧・続きの読み込み・新着バナー・投稿・編集・削除。**今まで `HomePage` にあった中身を、そのまま移した** |

違うのは「どの API を呼ぶか」だけ。`useTimeline(fetchPage)`（読み先を渡せる作り。プロフィールで、すでに使っていた）と、`useNewPostsCount(after, fetchCount)`（件数を調べる関数を渡せるようにした）に、`kind` ごとの関数を渡す。

```
all:       fetchPosts          / fetchNewCount（省略）
following: fetchFollowingPosts / fetchFollowingNewCount
```

- **関数は、毎回同じ物を渡す**（画面の外に、表で置いた）。毎回新しく作ると、「変わった」と見なされて、読み込みが何度も走る（`useCallback` の約束）
- 既存のテスト（165 件）は、1 件も直さずに通った。「中身を移しただけ」の変更が、壊れていない証拠になる

## 2. `key` で、タブごとに作り直す
`<Timeline key={kind} kind={kind} />`。**`key` が変わると、React は別の部品として、最初から作り直す**（プロフィールの、別ユーザーのときと同じ流儀）。

- わざと `key` を外すと、4 件のテストが落ちた。全体の投稿が残ったまま、「フォロー中」の投稿が、あとから足される（続きの目印や、新着の基準も、前のタブの物が残る）
- ログアウトしたときは、`const kind = user ? selected : 'all'` で、自動的に「全体」に戻す（タブも消える）

## 3. 「フォロー中」で投稿したときのお知らせ（TL-1）
自分の投稿は、「フォロー中」に入らない（自分はフォローできない）。投稿したのに、その画面に出ないと不安になるので、お知らせを出す。

- 「全体」：`onDone = prepend`（一番上に足す）
- 「フォロー中」：`onDone = () => setPostedNotice(true)`（足さない。お知らせを出す）
- わざと分岐を消すと、狙った 1 件（「フォロー中」で投稿 → お知らせ）だけが落ちた

## 4. 確かめたこと
- テスト：新しく 7 件（タブの出方、読み先、空の案内、投稿のお知らせ、新着の確認先）。全体で 172 件
- **わざと壊して、1 回に 1 か所**：`key` を外す → 4 件／お知らせの分岐を消す → 1 件／新着の確認先を「全体」に戻す → 1 件
- 本物のブラウザ（Chrome DevTools MCP）と本物のバックエンドで、通した：誰もフォローしていないと空の案内 → プロフィールでフォロー → 「フォロー中」に、フォローした人の投稿だけが新しい順に出る（フォローしていない人・自分の投稿は出ない）→ 「フォロー中」で投稿 → お知らせが出て、一覧には足されない → ログアウトで「フォロー中」のタブが消える

## 5. つまずき・気づき
- **全体のテストで、`登録すると、…` の 1 件が、5 秒の制限で落ちた。** `main` のままでも、同じように落ちた（変更をしまって、確認した）ので、今回の変更が原因ではない。単独で動かすと 1.9 秒。全体を並べて動かしたときだけ遅くなる（記録の F20）。**原因を疑うときは、「変更を外して、同じ結果になるか」で確かめる**
- 整形のチェック（Prettier）が、関数の宣言の 1 行が長すぎると、失敗した。`prettier --write` を、そのファイルだけに使って直した
