# 復習 C：投稿 API・SQL の基本・N+1 の入口

2026-11-17。復習 A（[ノート 08](08-review-a.md)）の続き。復習の途中で、ユーザーが「id が何か分からない」「SQL は DB の言葉？」と聞いてくれた。**土台の理解を、先に固める**ことにして、その説明も、ここに残す。

## 1. 土台：id・user_id・SQL

### id ＝ 表の 1 行ごとに付く、整理番号
出席番号や診察券番号と同じ。`posts` 表（投稿の表）は、こういう形。

| id | user_id | body | created_at |
|---|---|---|---|
| 1 | 3 | こんにちは | 11/16 10:00 |
| 2 | 5 | はじめまして | 11/16 10:05 |
| 3 | 3 | 今日は晴れ | 11/16 10:20 |

- **1 行 ＝ 1 件の投稿**
- `id` は、**投稿されるたびに、DB が自動で、1、2、3…と振る**（定義の `BIGSERIAL`）。だから、**id が大きいほど新しい**。`ORDER BY p.id DESC`（大きい順）が、新しい順になる
- **一度付いた id は、変わらない。** 消された投稿の番号は、欠番になるだけで、再利用されない

### user_id ＝ 「この投稿を書いた人」の印
番号は 2 種類あり、**別々の表の、別々の番号**。

| 名前 | どこの番号 | 意味 |
|---|---|---|
| `posts.id`（`p.id`） | 投稿の表 | この投稿の整理番号 |
| `users.id`（`u.id`） | ユーザーの表 | この人の整理番号 |
| `posts.user_id` | 投稿の表の中 | この投稿を書いた人の `users.id` |

`JOIN users u ON u.id = p.user_id` は、「投稿の `user_id` と、ユーザーの `id` が同じ行を、くっつけて」。だから、投稿者の名前も、一緒に読める。

### SQL ＝ DB に話しかけるための、決まった書き方の「注文票」
Java の言葉は、DB には通じない。DB への頼みごとは、SQL で書く。`Mapper`（倉庫番）が、SQL を書く係なのは、そのため。基本は 4 つだけ。

| 注文 | 意味 | 投稿での例 |
|---|---|---|
| `SELECT` | 探して、読む | タイムラインを読む |
| `INSERT` | 新しく入れる | 投稿する |
| `UPDATE` | 書き換える | 編集する |
| `DELETE` | 消す | 削除する |

## 2. 問題と答え

**C-1. ページ番号方式をやめて、「`before` ＝ 一番古い投稿の `id`」方式にしたのは、なぜ？**
- 自分の答え：新しい投稿があると、2 ページ目にずれが出て、重複する
- 補足：1 回目と 2 回目の間に、新しい投稿が入ると、古い投稿が後ろへ押し出され、1 ページ目の最後が、2 ページ目の先頭にも出る。`before=11`（「11 より古いもの」）方式は、新しい投稿が入っても、条件が変わらないので、ずれない

**C-2. SQL の値の埋め込みに、`#{}` を使い、`${}` を使わないのは、なぜ？**
- 自分の答え：分からない（コードのルールが分からない）
- 説明：**`#{}` は「穴あきの注文票」。** 注文票の形が先に決まり、穴に入れる値は、あとから、**ただの値**として渡される。**`${}` は「文章をそのまま貼り付ける」方式。** 利用者の入力が、命令の一部になってしまう（SQL インジェクション）。例：検索欄に `x' OR '1'='1` と入れられると、`WHERE username = 'x' OR '1'='1'` になり、`1=1` が常に正しいので、**全員が出てくる**。`#{}` なら、ただの文字列として探すので、何も出てこない
- ルール：**値は、必ず `#{}` で渡す。** 数字（`before`）でも、常に同じ書き方にして、事故を防ぐ。ユーザー検索（これから作る）で、実際に出会う

**C-3. 投稿 20 件を読んで、投稿者を 1 件ずつ探しに行くと、SQL は何回走る？**
- 自分の答え：40 回（仕組みは、さっぱり分からない）
- 正解：**21 回**（投稿を読む 1 回 ＋ 投稿者を探す 20 回）。これが **N+1 問題**（N 件の一覧に、1 回 ＋ N 回）
- 今は、`JOIN` で 1 回にまとめているので、**1 回**。**コメント・いいねで、本当の問題になる**：投稿 1 回 ＋ いいね数 20 回 ＋ コメント数 20 回 ＝ 41 回。解決の方向は、**20 件ぶんを、まとめて 1 回で聞く**（`GROUP BY` で、投稿ごとの数を一度に数える）。実装のときに、一緒にやる

**C-4. `UPDATE ... WHERE id = #{id} AND user_id = #{userId}` の、`AND user_id` は、なぜ要る？**
- 自分の答え：書いた人だけが書き換えられ、他の人は、条件に合わないので、更新できない
- 補足（品質チェック B8）：もうひとつの役目がある。**「確かめる」と「更新する」の間は、ゼロ秒ではない。** その隙間に、別のタブで削除されると、昔のコードは、「0 件だった」ことを見ずに、成功したつもりで進んだ。今は、SQL が「変わった件数」を返し、**0 件なら 404**。確かめることと書き換えることが、**1 つの SQL の中で同時に**行われるので、割り込めない
- まとめ：`AND user_id` は、**他人の物を守る**のと、**隙間をなくす**の、二役。Service の確認が、もし抜けていても、DB 自身が、他人の物は書き換えない（二重の守り。A-3 の「画面でも、サーバーでも」と、同じ考え方）

## 3. 学んだこと
- **「id が何か分からない」と、はっきり聞けたことが、一番の収穫。** 土台が分からないまま進むと、あとで、全部が分からなくなる。学習が進んでいるかどうかは、「全部分かること」ではなく、**どこが分からないかを、言えること**
- **「分からない」は、まだ習っていない・体験していないだけ。** SQL インジェクションは、ユーザー検索で、N+1 は、コメント・いいねで、実際に出会う。そのとき、たとえ（穴あきの注文票、1 + N）が、助けになる
- **予想を立ててから、答えを見る。** 外れても、予想した分だけ、頭に残る
